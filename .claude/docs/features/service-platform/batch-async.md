# Пакетный режим и асинхронные задания

Часть фичи `service-platform` — сначала [`index.md`](index.md).
Две **разные оси**, которые **комбинируются**: batch (много элементов за раз) и
async-large (большие файлы вне синхронного запрос-ответа). Пакет может исполняться
как задание; большой элемент внутри пакета — обрабатываться потоково.

## Пакетный режим (batch)

Каждая операция доступна в пакетном варианте: на вход — массив элементов (до
конфигурируемого лимита), на выходе — массив результатов **в том же порядке**.

- **Единичный вызов — частный случай пакета из одного элемента.** Общий кодовый
  путь и единый контракт — отдельной логики для «одного» нет.
- **Изоляция ошибок:** сбой одного элемента не роняет пакет. У каждого элемента —
  свой статус/`libError`; сводка по пакету (`total`/`succeeded`/`failed`).
  Политика — запросом: `continue-on-error` (по умолчанию) или `fail-fast`.
- **Общие параметры на пакет** (ключ/`KeySource`, флаги формата, политика
  валидации) задаются один раз и переопределяются на уровне элемента.
- **Параллелизм и порядок:** элементы распределяются по пулу воркеров, результаты
  собираются с сохранением исходного порядка. Конкурентность и объём пакета
  ограничены конфигом (RAM + защита нативной либы).
- **Стриминг больших пакетов:** gRPC — server-streaming результатов; REST —
  опционально NDJSON-поток (не держать весь ответ в памяти). MQ — по элементу с
  `correlationId`.

REST: `POST /{op}/batch` (`/sign/batch`, `/verify/batch`, `/extract/batch`,
`/cert/info/batch`, `/cert/validate/batch`) с `{ items: [...], policy,
concurrency }` → `{ total, succeeded, failed, results: [...] }`. Каждый
`results[i]` — `{ index, status, output? , error? }`, `status ∈
ok|error|skipped` (skipped — при fail-fast). NDJSON-стрим включается заголовком
`Accept: application/x-ndjson` или `?stream=1`: по объекту-строке на элемент (в
порядке завершения, с `index` для пересборки) + финальная summary-строка
`{total,succeeded,failed}`. CLI/MQ используют тот же контракт через
op-имена `<op>-batch` (агрегированный ответ, без стрима).

> **Структурная vs операционная ошибка.** Изоляция ошибок — про сбой
> *операции* элемента (неверный пароль ключа, битая подпись): он попадает в
> `results[i].error`, пакет продолжается. Структурно битый элемент (неизвестный
> `format`/`encoding`) — это ошибка *запроса*: она обрывает пакет с `400`
> (указан индекс), а не превращается в пер-элементный статус.

**Реализация (batch).** Доменное ядро — `core.runBatch` (generic; порядок,
изоляция, fail-fast, ограниченная конкуренция, сток для стрима) + методы
`Service.SignBatch/VerifyBatch/…`. Транспорт: `dto.BatchRequest[R]`, роутер
`dispatch` (op-имена `*-batch`), REST-хендлеры со стримом. gRPC — **реализовано**:
`rpc <Op>Batch(<Op>BatchRequest) returns (stream <Op>BatchEvent)`, где событие —
`oneof { item, summary }` (по элементу + финальная сводка); контракт в
`api/qoltanba/v1/service.proto`, генерация `protoc --proto_path=. --go_out=.
--go-grpc_out=. --*_opt=paths=source_relative api/qoltanba/v1/service.proto`. MQ —
**реализовано**: `dispatch.HandleStreaming` + callback-модель `mq.Processor`
(`PublishFunc`) публикуют по reply-сообщению на элемент + summary под одним
`correlationId` (адаптеры amqp/kafka/nats шлют несколько reply; ack — после всех,
requeue может пере-стримить элементы → клиент дедуплицирует по `index`).

## Асинхронные задания и большие файлы

Синхронный запрос-ответ непригоден для больших файлов (таймауты, всплеск RAM, +33%
overhead base64 в JSON). Для них — модель заданий (jobs) и потоковая обработка.

- **Модель задания:** клиент отправляет задание → получает `jobId` и `202
  Accepted` → узнаёт результат одним из способов: **опрос** статуса,
  **webhook-callback** по завершении, либо доставка через MQ. Жизненный цикл:
  `queued → running → succeeded|failed|cancelled`, с прогрессом, TTL и отменой.
- **Идемпотентность submit:** `Manager.SubmitIdempotent` — повтор с тем же
  idempotency-ключом (REST `POST /jobs`: тело `idempotencyKey` или заголовок
  `Idempotency-Key`; MQ `job-submit`: поле конверта) отдаёт **существующий** job, не
  создаёт дубль. Node-local best-effort — детали в [`transports.md`](transports.md#идемпотентность-безопасные-ретраи).
- **Вход/выход по ссылке, а не inline:** большие данные — как **путь к файлу** или
  ссылка на объектное хранилище (S3-совместимое)/стрим-загрузка, не base64 в теле.
  Держит RAM низкой, убирает overhead base64.
- **Потоковая обработка с опорой на возможности библиотеки:** где либа читает файл
  сама (`KC_IN_FILE`, файловые `ZipConSign`/`ZipConVerify`) — отдаём путь, не
  буферизуя. Для очень больших входов — схема **hash-streaming → `SignHash`** и
  **detached-подпись** (не тащим данные в подпись).
- **Хранилище состояния заданий (`JobStore`) — за портом, лестница durability:**
  сервис **не бандлит брокер** (противоречит «тонкий/переносимый»: навязывать
  Erlang-рантайм и его эксплуатацию нельзя) — он **клиент** к инфраструктуре
  потребителя. Уровни:
  - *эфемерный* — in-memory (быстро, дефолт для stateless-деплоя);
  - *встраиваемый durable* — **on-disk `bbolt`** (чистый Go, один файл, ноль внешних
    зависимостей): in-flight задания переживают рестарт/деплой одного узла **без
    внешнего брокера**. Это ответ на «не потерять при перезагрузке», не требующий
    поднимать Rabbit;
  - *HA / горизонтальное масштабирование* — внешний стор (БД/Redis) и/или доставка
    через MQ потребителя с at-least-once + идемпотентность по `jobId`.
- **Семантика восстановления после рестарта:** задание в состоянии `running` нельзя
  «продолжить с середины» крипто-вызова — при старте оно **откатывается в `queued`
  и переисполняется целиком**. Это безопасно: крипто-операции идемпотентны по входу,
  без побочных эффектов (гарантия дедупликации результата — по `jobId`).
- **Backpressure и лимиты:** большие задания идут через отдельную очередь поверх
  пула воркеров; конфигом ограничены число параллельных больших заданий,
  максимальный размер входа и место под спул на диске.

REST: `POST /jobs` (`{ op, request, callbackUrl? }`) → `202` + `Location:
/jobs/{id}` + статус-вью → `GET /jobs/{id}` (статус) → `GET /jobs/{id}/result`
(`200` = вывод операции; `409` = ещё не готово; `422` = failed/canceled) →
`DELETE /jobs/{id}` (отмена, идемпотентно). gRPC — **реализовано**: unary
`SubmitJob`/`GetJob`/`GetJobResult`/`CancelJob` (`JobStatus`-вью; `GetJobResult`
отдаёт вывод операции как JSON-байты, `ErrNotReady`→`FailedPrecondition`). MQ —
**реализовано** как envelope-ops `job-submit`/`job-status`/`job-result`/
`job-cancel` (модель опроса, как REST-поллинг; менеджер не завязан на брокер-
publisher). **Отложен** только push результата в reply-назначение по завершении
(требует брокер-publisher в менеджере).

**Реализация (jobs).** Пакет `internal/jobs`: `Manager` (пул воркеров, отдельная
очередь с backpressure → `ErrBusy`/`503`, TTL-reaper, отмена, webhook, recovery,
graceful drain), порт `Store` с реализациями `MemStore` (эфемерный, дефолт) и
`BoltStore` (bbolt, файл `0600`). `Executor` инъектится из `main` как замыкание
над `dispatch.Handle`, поэтому пакет не знает ни о крипте, ни о транспортах и
**batch-op выполняется как задание** тем же путём (комбинация осей). Конфиг —
`jobs.enabled/store/bolt-path/max-concurrent/queue-size/max-input-mb/ttl`
(включается флагом, обслуживается по REST). Слишком большой inline-вход → `413`
(`max-input-mb`).

**Гигиена секретов (jobs).** Наружу отдаётся только `jobs.View` (id/статус/
тайминги/ошибка) — **никогда** `Request` (может нести пароль/PIN/ПДн) или
`callbackUrl`; `Request` затирается при переходе в терминальное состояние. Файл
bbolt держит payload'ы на диске до завершения задания — поэтому `0600` (см.
[`observability-security.md`](observability-security.md)).

**Вход-по-ссылке — реализовано** (порт `core.DataResolver`, инфра
`internal/dataref`). `SignInput`/`VerifyInput` несут `DataRef{Path, URL}`; резолвер
отдаёт локальный путь, а драйвер читает файл сам через **`KC_IN_FILE`** (флаг
0x8000; `provider.SignRequest/VerifyRequest.Path`) — весь объём **не буферизуется
в Go**. CMS-only. **Безопасность:** оба источника opt-in (`input.allow-local-path`
— риск чтения произвольных файлов; `input.allow-url` — SSRF), URL под allow-list
схем (дефолт https; S3 — через presigned-HTTPS, без SDK), потоково в приватный
спул-файл `0600` с cap по размеру (`input.max-mb`) и **гарантированной очисткой**
(`ResolvedData.Release`, в т.ч. при сбое/отмене); тексты ошибок не содержат
путь/URL. **Отложено:** файловые `ZipConSign`/`ZipConVerify`, XML/WSSE by-ref и
альтернатива hash-streaming `HashData`→`SignHash` (для CMS её роль закрывает
`KC_IN_FILE`).
