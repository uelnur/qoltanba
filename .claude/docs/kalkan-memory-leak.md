# Утечка памяти в Kalkan — ~1 МБ на verify CMS, ~0.5 МБ на certInfo

Второй (после [double-free](kalkan-native-flake.md)) дефект проприетарной библиотеки, замеренный на реальном материале: **нативная память растёт линейно с числом операций и не возвращается**. Наш Go-код и cgo-обвязка чисты — течёт библиотека. Читать при: планировании памяти под прод, разборе OOM/роста RSS, оценке готовности к продакшену, эскалации вендору.

## Замеры (soak, реальный Kalkan, linux/amd64)

`test/e2e/soak_e2e_test.go`, 400–1000 итераций, `QOLTANBA_SOAK=<N>`; RSS из `/proc/self/status`, Go-heap из `runtime.MemStats` в тех же точках.

| Операция | Рост RSS на вызов |
|---|---|
| **verify CMS** (`kc_verify_data`) | **~1 000 КБ** |
| **certInfo** (loadKey + export + 30 × `kc_cert_info`) | **~500–590 КБ** |
| verify XML | ~15 КБ |
| sign XML | ~16 КБ |
| sign CMS | ~13 КБ |

Полный микс (2 sign + 2 verify + certinfo) — **~2 МБ на итерацию**: 233 МБ → 1.81 ГБ за 900 итераций, линейно, без насыщения. Прогон с trust-store и без него дал **одинаковый** рост, то есть повторная загрузка CA (`X509LoadCertificateFromFile` на каждый вызов) ни при чём.

**Течёт не наш код:**

- Go-heap плоский на всех прогонах (460–620 КБ от начала до конца) — рост целиком вне Go.
- Дескрипторы, дочерние процессы, зомби, временные файлы — плоские (15 / 1 / 0 / 0).
- Утечка **не зависит от размера наших буферов**: уменьшение `verifyData` с 1 МБ до 128 КБ и `certInfo` с 64 КБ до 4 КБ дало те же 1 000 КБ и 593 КБ на вызов. Сами буферы освобождаются на всех путях (`withBuf`, `defer C.free`).
- Функции освобождения в C-API нет: в экспортах `libkalkancryptwr` есть `KC_Finalize`/`KC_XMLFinalize`/`KC_Pkcs11_Finish`, но ни `KC_FreeBuffer`, ни `KC_CloseKeyStore` — освободить накопленное изнутри процесса нечем.

## Что это значит для прода

Считать по профилю нагрузки: сервис, делающий 1 verify CMS/с, набирает **~3.5 ГБ/час**; 10/с — тот же объём за 6 минут. Долгоживущий процесс без перезапуска обречён на OOM. При этом под большим RSS всплывают и краши: soak-прогон с trust-store упал `SIGSEGV` в `kc_load_cert_file` на ~1.4 ГБ.

**Единственный работающий сброс — граница процесса** (та же причина, что и у double-free: `kc_close` не финализирует библиотеку).

## Митигация отгружена (замерена)

`internal/cryptoworker` (включён по умолчанию): сервис не грузит библиотеку вовсе, все операции идут в дочерние процессы, которые рециклятся по бюджету **памяти** (`crypto-worker.max-rss-mb`, 512 МБ) и операций (`max-ops`, 1000). Механика, конфиг и краш-часть — [`kalkan-native-flake.md`](kalkan-native-flake.md).

Тот же soak (1000 итераций микса) с воркером:

| | Без воркера | С воркером |
|---|---|---|
| RSS главного процесса | 233 МБ → 1.81 ГБ | **23 МБ → 19.8 МБ** (плоский) |
| RSS ребёнка | — | пилой 237 → 142 → 40 → 194 → 98 → 27 МБ (рециклится, потолок = бюджет) |
| fd / зомби / temp | плоские | плоские |

То есть потребление стало **ограниченным сверху**: родитель ~20 МБ плюс до `processes × max-rss-mb`. Утечка никуда не делась — она просто регулярно выбрасывается вместе с процессом; стоимость — перезапуск библиотеки (сотни мс) раз в N операций, на пути запроса он виден только первому вызову после рециклинга.

**Вендор-эскалация** всё равно нужна вместе с репро double-free: течёт нормальный, ежедневный путь (`verify`), репро воспроизводим одной командой.

## Как перезамерить

```
QOLTANBA_SOAK=1000 test/functional/run.sh -run TestSoakResourceGrowth              # прод-схема (воркер)
QOLTANBA_CRYPTO_WORKER=0 QOLTANBA_SOAK=1000 test/functional/run.sh -run TestSoakResourceGrowth   # in-process, видно утечку
```

Сужающие переключатели (для локализации): `QOLTANBA_SOAK_ONLY=sign-cms|verify-cms|sign-xml|verify-xml|certinfo`, `QOLTANBA_SOAK_NO_VALIDATE=1`, `QOLTANBA_SOAK_NO_TRUST=1`. Тест сам печатает снимки (RSS, Go-heap, дети, fd, зомби, temp-файлы) и падает, если растут дескрипторы/процессы/временные файлы — то есть отдельно ловит регресс **нашей** стороны.

Прогон с прод-OCSP держать коротким: после ~1000 запросов респондер `ocsp.pki.gov.kz` начинает отвечать медленно (в одном прогоне валидация упёрлась в 60-секундный таймаут воркера).
