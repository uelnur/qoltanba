# Валидация, цепочка, trust-store

Часть фичи `signature-service` — сначала [`index.md`](index.md).
Проверка статуса (OCSP/CRL) и построение цепочки до корня (доменный слой). Механика
C-API (`X509ValidateCertificate`, флаги, достройка цепочки, коды) — в
[`../../kalkan-api/certificates.md`](../../kalkan-api/certificates.md); CA-реестр —
[`nuc-pki-reference.md`](../../nuc-pki-reference.md).

## Построение цепочки

**Единого вызова, возвращающего `[leaf, intermediate, root]`, в API нет.** Цепочка
достраивается, потому что **в подписи вложен только лист** (НУЦ/КУЦ там нет —
проверено: `KC_GetCertFromCMS` отдаёт лист). Три источника CA:

1. **Доверенный bundle потребителя** (BYOL): загрузить корень
   `X509LoadCertificateFromFile(path, KC_CERT_CA)` и промежуточный
   `…KC_CERT_INTERMEDIATE`, затем `X509ValidateCertificate` строит цепочку.
2. **Дозагрузка по AIA** (проверено онлайн; код достройки — в
   [`../../kalkan-api/certificates.md`](../../kalkan-api/certificates.md)): из DER листа
   берётся URL `CA Issuers` → издатель скачивается по HTTP → разбирается → обход
   вверх, пока есть ссылка (у корня её нет). **Нюанс:** AIA промежуточного может
   указывать на **другой хост** (`root.gov.kz`, не `test.pki.gov.kz`) — не
   завязываться на один домен. В проде: таймауты, лимит переходов, кэш, доверять
   корню только если он в trust-store.
3. **Конфигурируемые URL** со скачиванием/кэшем/рефрешем — дефолтный набор из
   официального CA-реестра РК (`internal/pki/ca-registry.json`).

Порядок восстанавливается по `authorityKeyIdentifier` листа = `subjectKeyIdentifier`
издателя; корень самоподписан (`SUBJECT_DN == ISSUER_DN`). CA-уровень опознаётся по
`keyUsage=keyCertSign cRLSign` + отсутствию EKU (см. [`certificates.md`](certificates.md)).
**Надёжный выбор издателя** (когда достраиваем сами): кандидат, у которого
`subjectDN == issuerDN` листа **и** подпись листа проверяется его открытым ключом —
одного совпадения DN мало (DN не уникален); самоподписанный → родителя нет.

Тестовая цепочка: `leaf` → НУЦ (`CN=ҰЛТТЫҚ КУӘЛАНДЫРУШЫ ОРТАЛЫҚ (GOST) TEST 2022`)
→ КУЦ (`CN=НЕГІЗГІ КУӘЛАНДЫРУШЫ ОРТАЛЫҚ (GOST) TEST 2022`).

В ответе `chain[]` — **best-effort**: лист гарантирован, полная цепочка требует
CA-источника → отдаём признак «неполная / нет якоря доверия».

> **Текущая реализация (nascent):** доменный слой строит цепочку от листа вверх по
> кандидатам из доверенного набора (trust-store + CA из запроса). **Выбор издателя
> усилён проверкой подписи** там, где Go умеет (RSA, `CheckSignatureFrom`):
> подтверждённый криптографически издатель выигрывает; для **ГОСТ** (Go проверить
> не может) — фолбэк на `authorityKeyIdentifier→subjectKeyIdentifier`, затем
> `issuerDN==subjectDN`; кандидат с заведомо неверной подписью отбрасывается.
> **AIA-дозагрузка (источник 2) — реализована** (`internal/aia`, опция
> `trust.fetch-aia`): недостающий издатель качается по `CA Issuers` URL —
> **DER, PEM и PKCS#7-`.p7c`** (certs-only SignedData разбираем сами, без
> зависимости) — с таймаутом/кэшем/лимитом размера; догруженные серты в цепочке, но
> **якорями доверия не считаются** (пока не сойдутся на корень из trust-store).
> **Источник 3 — реализован** (`trust.LoadRegistry`, опция `trust.use-rk-registry`):
> якоря преднагружаются из официального реестра КУЦ (`internal/pki/ca-registry.json`)
> скачиванием каждого CA по URL (best-effort, промахи логируются;
> `trust.rk-include-test` — тестовые корни). `chainComplete` = дошли до
> самоподписанного; `trustAnchorFound` = узел есть в trust-store. Подпись всего
> документа проверяет Kalkan (`verify`).
> **Авто-обновление trust-store — реализовано** (`trust.Refresher`, опция
> `trust.refresh-interval`): фоновый воркер периодически перестраивает набор якорей
> из обоих источников (RK-реестр + `trust.ca-dir`) и атомарно подменяет снапшот в
> потокобезопасном `trust.Store` — сервис подхватывает изменения реестра и новые
> локальные CA без рестарта. Дефолт **auto**: 24h при `use-rk-registry`, иначе выкл;
> `0`/`off` — явно выкл. Best-effort: пустой ребилд (транзиентный сбой сети) **не
> затирает** последний рабочий набор (keep-last-good). Статус (вкл/интервал/
> последнее время/число якорей/ошибки) — в `/statusz.trustRefresh`.
> **Криптопроверка цепочки (вкл. ГОСТ) — реализована** (опция `trust.verify-chain`):
> домен делегирует в Kalkan `X509ValidateCertificate` с `KC_USE_NOTHING` (офлайн,
> без OCSP/CRL) — загружает CA-узлы построенной цепочки + якоря и проверяет лист;
> `RawCode==0` → признак `chainSignaturesVerified` на подписанте (`KCR_CHECKCHAINERROR`
> → false, не фейл операции). Это единственный путь проверить ГОСТ-подписи цепочки:
> Go их не умеет, Kalkan — да. Go-построитель остаётся быстрым структурным слоем и
> источником цепочки для этого вызова.

> **AIA-догрузка кормит и крипто-верификацию (не только `chain[]`).** Раньше
> AIA-fetched/Go-построенные промежуточные серты попадали только в поле `chain[]`, а
> сам `VerifyCMS`/`ValidateCert` получал лишь якоря trust-store — поэтому боевой лист,
> чей издающий НУЦ доступен по AIA, но не преднастроен, не якорился (`0x08F00042`).
> Исправлено (`core.Service`): **verify** — retry-on-anchor-failure (при
> cert-time-ошибке достраиваем цепочку подписантов через AIA, добавляем найденные
> intermediate в trusted и повторяем verify **один раз**; только на fail-пути, обычный
> кейс не платит); **validate** — проактивная AIA-достройка (серт известен заранее).
> Параллельно официальный CA-реестр (`ca-registry.json`) дополнен ежегодными
> издающими НУЦ (`nca_gost_2022`/`nca_rsa_2022`), которых нет на индексе реестра, но на
> которые ссылаются боевые листы через AIA (seed в `tools/oidgen/fetch_ca_registry.py`).

## OCSP / CRL

`X509ValidateCertificate(cert, validType, validPath, checkTime, outInfo, …, flag,
getOCSPResponse, …)`:

- **OCSP** (`validType=KC_USE_OCSP`, `validPath="http://…/ocsp/"`, сетевой; проверено
  на живом сервисе):
  - **валидный** → rc `0x00000000`, `outInfo`: `OCSP: … status: good … This Update:
    … Next Update: …`; при флаге `KC_GET_OCSP_RESPONSE` — **base64 OCSP-ответа** (~6.4 КБ);
  - **отозванный** → rc `0x00000001`, `outInfo`: `… status: revoked … Reason:
    certificateHold … Revocation Time: …`.
  - Статус (good/revoked/unknown) — из **rc и** текста `outInfo`.
- **CRL** (`validType=KC_USE_CRL`, `validPath`=путь к `.crl`) — офлайн по файлу; в
  прогоне вернула нестандартный `0x08F0005D` (вероятно устаревший офлайн-CRL). Для
  надёжной онлайн-проверки статуса предпочтителен OCSP. При собственной проверке —
  **delta-CRL раньше полного**.

**Если строим OCSP-запрос сами** (не через `X509ValidateCertificate`): CertID-хеш —
**всегда SHA-256**; nonce — 8 случайных байт в двойном `DEROctetString`, расширение
`id-pkix-ocsp-nonce`, `critical=false`; POST `Content-Type: application/ocsp-request`;
запрос **не подписан**; **AIA из сертификата игнорируется** — URL только из конфига.
**Interop-ловушка:** отдельные OCSP-серверы РК могут требовать иной CertID-хеш —
держать как риск совместимости.

**Улучшение над эталоном:** проверять **подпись OCSP-ответа и thisUpdate/nextUpdate**,
а также подпись/nextUpdate CRL (см. [`ncanode.md`](../../ncanode.md) — там это не
делается).

> **Реализовано (структурный разбор):** вердикт good/revoked даёт Kalkan; домен
> дополнительно парсит поля. **OCSP** — `golang.org/x/crypto/ocsp` (без проверки
> подписи, `issuer=nil`: Kalkan уже дал доверенный вердикт; RSA-подпись сверяема,
> ГОСТ Go не умеет) → `thisUpdate`/`nextUpdate`/`producedAt`/`revocationTime`/
> `reason`; фолбэк на `reason` из текста `outInfo` для ГОСТ. **CRL** —
> `x509.ParseRevocationList` (stdlib, структурно; ГОСТ-подпись сверяет Kalkan) →
> `thisUpdate`/`nextUpdate` + запись отзыва цели (`revocationTime`/`reason`).
> Вход `Validate`: `responderUrl` (OCSP) или `crl` (байты; домен пишет во временный
> файл для Kalkan и параллельно парсит). Сырой OCSP-ответ отдаётся только при
> `wantOcsp`.
> **CRL-кэш «own-fetch + library-verify» — реализован** (`internal/crl.Cache`,
> порт `core.CRLSource`, опция `trust.crl-cache`): при `method=crl` **без** inline-`crl`
> домен тянет CRL по CDP сертификата (`CRLDistributionPoints`) через кэш по URL,
> обновляемый **по `nextUpdate`** (refresh-ahead, не по факту запроса); при сбое
> повторного скачивания — фолбэк на последний кэш (stale-but-available, помечен
> не-свежим). Дальше — тот же путь: временный файл →
> `X509ValidateCertificate(KC_USE_CRL)` (Kalkan проверяет подпись+свежесть). OCSP
> остаётся авторитетным для real-time статуса.
>
> Три пункта design-раздела ниже **реализованы**:
> - **Диск-спул** (`trust.crl-spool-dir`, `trust.crl-cache-max-mb`): при заданной
>   директории тела CRL живут на диске (ключ = sha256 URL), метаданные — в RAM; кэш
>   **переживает рестарт** (warm-start сканирует директорию и подхватывает валидные
>   файлы), общий размер ограничен с **LRU-вытеснением**. Пустой spool-dir → in-memory.
> - **Delta↔base-согласованность:** если у серта есть Freshest-CRL (delta CDP), слой
>   тянет и delta, проверяет `delta.BaseCRLNumber ≤ base.CRLNumber` и совпадение AKI;
>   согласованный свежий delta возвращается для **структурного overlay** отзыва (домен
>   накладывает отзыв, которого нет в base — safe direction: только добавляет отзыв).
>   `core.CRLResult{Base, Delta, Reliable, Reason}` — контракт порта.
> - **soft/hard-fail-политика** (`trust.crl-fail-policy`, домен `core.WithCRLFailPolicy`):
>   при недоступном/протухшем/рассогласованном CRL **soft** (дефолт) уводит на OCSP с
>   warning `crl: fallback-to-ocsp:<reason>`, **hard** — `KindInvalid` (fail-closed).
>   Inline-`crl` от вызывающего используется как есть (политика не применяется).

Ответ валидации: `status`, `reason` + `revocationTime` (для revoked),
`thisUpdate/nextUpdate/producedAt`, сырой OCSP-ответ (base64), тип проверки.

**`status.determinate`** отделяет «ответ получен» от «спросить не удалось». Kalkan
отдаёт недостижимый респондер как soft-failure с `revoked=false` — форма ровно та же,
что у чистого ответа, поэтому неустановленный статус помечается явно (`StatusUnknown`
от драйвера или soft-failure ⇒ `determinate=false`). Читать `revoked=false` без
`determinate` — это и есть fail-open.

## Цепочка по запросу (`buildChain`) и тестовые якоря

- **`cert-info` строит цепочку, когда её просят.** Флаг `buildChain` был объявлен в
  контракте, задокументирован и выставлен наружу по gRPC — и **не читался**: цепочка
  всегда возвращалась пустой. Теперь собирается из trust-store плюс AIA, с warning'ом,
  когда не доходит до самоподписанного корня или упирается не в настроенный якорь.
- **`trust.rk-include-test` добавляет тестовые якоря, а не заменяет ими боевые.**
  Фильтр `CACertificatesFor` сравнивал `c.Test == test`, то есть включённый флаг
  оставлял стенду **только** три тестовых корня и лишал доверия ко всему настоящему —
  ровно наоборот тому, что обещает имя.

## Адрес респондера: из сертификата, а не из умолчания библиотеки

При пустом `responderUrl` в библиотеку уходил пустой путь, и она шла к **своему
встроенному умолчанию — боевому респонденту**, который о сертификате из тестового
контура ничего не знает. Проверка проваливалась, а без `determinate` это читалось как
«не отозван».

Теперь адрес берётся из **AIA самого сертификата** (`ocspURLFromCert`, только
`http(s)`), явный `responderUrl` по-прежнему побеждает. **Сертификат, который не
публикует респондера, оставляет статус неустановленным** (`determinate: false` +
warning), а не уходит к умолчанию: угадывание респондента — ровно то, что делало эту
поломку молчаливой. Замерено на живом тестовом УЦ: адрес резолвится в
`http://test.pki.gov.kz/ocsp/` без единой настройки.

## Отзыв внутри verify

`/verify` **проверяет отзыв сам и по умолчанию** (`VerifyInput.RevocationCheck`,
tri-state: `nil`=вкл). Раньше verify отзыв не смотрел вовсе, а `report` выдавал шаг
`revocation: skipped`, который вердикт игнорировал — подпись отозванным сертом
получала `verdict: valid`. Это единственный способ, которым сервис мог назвать
репудиированную подпись хорошей, поэтому:

- **`revoked` ⇒ `valid=false` и `verdict=invalid`.** Математика подписи цела, но ключ
  отозван; вызывающий, читающий `valid`, не должен помнить про второе поле.
- **Не установлено ⇒ `verdict=indeterminate`**, не `valid`. Касается и явного
  отключения (`revocationCheck:false`), и недостижимого респондера: вопрос остался
  открытым, а вердикт «валидно» это скрывает. Шаг диагноза `revocation` —
  `pass|fail|unknown`; `skipped` остался только для случая «подпись и так не сошлась».
- **Сеть экономится там, где нечего проверять:** при `valid=false` от библиотеки
  респондер не опрашивается — вердикт уже invalid по шагу `signature`.
- **`/verify/at` отключает inline-проверку осознанно** (`historical.go`): она отвечает
  «отозван ли сейчас» и утопила бы подпись, которая была хороша на X и отозвана позже —
  ровно тот случай, ради которого фича существует. Статус на X реконструируется ниже.
- Ручки запроса: `revocationCheck`, `revocationMethod` (`ocsp|crl`), `responderUrl`.
  Транспорты: REST/CLI/socket/MQ через DTO, gRPC — `optional bool revocation_check`
  (именно `optional`, иначе unset означал бы «выключить»).

> **Стоимость и риск.** Каждый verify теперь делает OCSP-вызов (смягчается
> `trust.ocsp-cache`). Отдельно: вердикт `revoked` по OCSP — триггер нативного
> дефекта Kalkan из [`../../kalkan-native-flake.md`](../../kalkan-native-flake.md),
> так что дефолт-вкл увеличивает частоту попадания в него; удерживается уже
> отгруженным `internal/cryptoworker`.

## Point-in-time (historical) validation

**«Была ли подпись валидна на момент X», а не «валидна сейчас».** Реализовано:
`core.Service.VerifyAt` (`internal/core/historical.go`), REST `POST /verify/at`, dispatch-
op `verify-at` (⇒ CLI/socket/MQ), DTO `VerifyAtRequest`. Отличается от LTV: LTV
*консервирует* доказательства при подписании, здесь мы *реконструируем* вердикт на
прошлый инстант из сегодняшних источников.

Временной вопрос раскладывается на три факта, оцениваемых на X, поверх обычного
`Verify` (он даёт математику подписи, серты подписантов и цепочку):

1. **подпись верна криптографически** — не зависит от X (берётся из `Verify`;
   `CheckCertTime` принудительно off — системные часы отвергли бы истёкший-сегодня,
   но валидный-тогда серт, ровно тот кейс, ради которого фича);
2. **серт был в окне действия на X** — `notBefore ≤ X ≤ notAfter` (из распарсенного
   серта, `withinValidityAt`);
3. **серт не был отозван на X** — реконструкция из **текущего** статуса.

**Ключ — монотонность отзыва.** OCSP/CRL дают *текущий* статус, но отзыв необратим
(единственное обратимое основание — `certificateHold` — помечается оговоркой). Поэтому
текущий статус + `revocationTime` отвечают о прошлом: `revoked-as-of-X ⟺ X ≥
revocationTime`. Good-сегодня ⇒ good на любой более ранний X; revoked-сегодня ⇒ был
good на X, если X предшествует отзыву. Источник ревокации — `s.Validate` по серту
подписанта (OCSP по умолчанию; для спорного инстанта точнее inline **архивный CRL** на
дату X, `method=crl`+`crl`).

**Детерминированность честная.** Вердикт несёт `determinate`: если серт отозван, но
`revocationTime` неизвестен, либо OCSP-респондер отказал по истёкшему серту, либо окно
действия серта неизвестно — `determinate=false` (не угадываем). Итог по документу —
конъюнкция по всем подписантам (`validAt`/`determinate`). Контракт: `VerifyAtOutput`
→ `[]SignerAt{Signer, PointInTimeVerdict}`; `PointInTimeVerdict` держит
`validAt/determinate/signatureValid/withinValidity/notRevokedAt/revokedAsOfAt/
revocationTime/reason` + человекочитаемые `reasons` (оговорки: обратимый hold,
неполные данные, отсутствующее окно). `at` в будущем/ноль — `KindInvalid`.

## Свой слой ревокации: что берём в домен, что оставляем Kalkan (design)

`X509ValidateCertificate` — монолит-чёрный-ящик: OCSP делает сам, а **CRL умеет
только офлайн по локальному файлу** — без скачивания, планового обновления, с плохой
обработкой устаревшего (`0x08F0005D`). Ни кэша, ни политики, ни метрик наружу не
отдаёт. Поэтому **жизненный цикл и политику ревокации забираем в домен**, а Kalkan
оставляем **только GOST-примитив проверки подписи**. Это даёт контроль, наблюдаемость,
тестируемость без либы и владение памятью — то, чего у монолита нет.

**Наш слой (Go-домен, cgo-free, фейкуется в юнит-тестах без Kalkan):**
- разрешение источников: CDP из сертификата / AIA / конфиг CA-реестра (`internal/pki/`);
- скачивание CRL с таймаутами/ретраями/лимитом переходов; delta-CRL раньше полного (см. выше);
- **кэш память+диск** с TTL, ограниченным размером и вытеснением; **refresh-ahead по
  `nextUpdate`**, а не по факту запроса; для больших CRL НУЦ — потоковый разбор + спул;
- политика свежести (`thisUpdate`/`nextUpdate`) и **soft-fail vs hard-fail** по конфигу
  (сеть недоступна → `warn` либо `invalid`);
- OCSP: nonce/anti-replay, переиспользование stapled-ответа (детали запроса — выше);
- **память на GC-стороне:** сеть/парсинг/кэш живут в Go (нет C-утечек на этом пути),
  cgo пересекаем только маленькими ограниченными verify-вызовами;
- метрики/логи/трейсинг ревокации (латентность OCSP, возраст/свежесть CRL, hit/miss кэша).

**Kalkan (за портом `Provider`):** собственно **GOST-верификация** подписи OCSP-ответа
и CRL — Go stdlib GOST не умеет. Два уровня:
- **MVP (работает, без новых примитивов):** мы скачиваем/обновляем/кэшируем CRL → отдаём
  **свежий файл** в `X509ValidateCertificate(KC_USE_CRL, path)`; Kalkan проверяет подпись
  и статус. Весь lifecycle-контроль — наш, а крипта — либина.
- **Самостоятельная GOST-верификация OCSP/CRL — Kalkan не поможет (подтверждено по
  таблице функций).** Verify экспортируется только для контейнеров (`VerifyData` CMS,
  `VerifyXML` XML, `ZipConVerify` ZIP); примитива «проверить GOST-подпись над
  произвольными байтами / данный OCSP-ответ» **нет** (детали —
  [`../../kalkan-api/certificates.md`](../../kalkan-api/certificates.md)). Значит
  self-verify требует **не-Kalkan GOST** (сторонняя либа/своя крипта) — это не-цель
  ([`../../architecture.md`](../../architecture.md)). GOST-математику оставляем Kalkan в
  его форматах: для CRL — файловый режим (выше), для OCSP — только сетевой вызов либы.

**Граница честная:** оркестрацию и политику забираем полностью, GOST-математика остаётся
в Kalkan — мы крипту не пишем ([`../../architecture.md`](../../architecture.md)), это
разделение, а не компромисс.

### Сетевой контроль OCSP: что даёт библиотека (подтверждено по API)

Асимметрия CRL vs OCSP — ключевая:
- **CRL:** `KC_USE_CRL` принимает **файл** → own-fetch + library-verify **работает**
  (мы владеем сетью, Kalkan проверяет подпись CRL и статус).
- **OCSP:** точка входа одна — `X509ValidateCertificate(KC_USE_OCSP)`, она **сама ходит в
  сеть**; отдать ей *принесённый нами* ответ **нельзя** (`getOCSPResponse` — только выход,
  OCSP-верификация OpenSSL не экспортирована). → **own-fetch + library-verify для OCSP
  невозможен.**

Что реально управляемо при делегировании OCSP:
- **Прокси — да:** `KC_SetProxy(flags, addr, port, user, pass)` (`KC_PROXY_ON/OFF/AUTH`).
  Глобально на экземпляр; hot-reload = пере-установка на **каждом** экземпляре пула.
- **Retry / exponential backoff / connection timeout — НЕТ** (только исход
  `KCR_OCSP_CONNECTIONERR`). Внутренний HTTP — чёрный ящик; доменный ретрай всего
  `X509ValidateCertificate` — тупой (заново и сеть, и крипта; нет per-attempt таймаута).

**Следствие.** Тонкий сетевой контроль (backoff/retry/timeout/метрики) над ревокацией
достижим через **свой CRL-слой**. Для **OCSP** выбор: (a) делегировать Kalkan
(+`KC_SetProxy`, без retry/backoff), либо (b) забрать целиком, но с **не-Kalkan GOST**-
верификацией ответа — не-цель ([`../../architecture.md`](../../architecture.md)).

### Известный дефект: `X509ValidateCertificate` и боевая GOST-2015-512 цепочка

Эмпирически (боевой лист НУЦ GOST 2022, лето 2026): `X509ValidateCertificate`
возвращает **`0x08F00042`** (`KCR_CERTTIMEINVALID`) для реального
`gost2015-512`-листа **даже когда** полная цепочка загружена (лист→`nca_gost_2022`
intermediate→`root_gost2015_2022` root, все связаны по AKI↔SKI и валидны по времени),
часы верны, а OCSP отвечает `successful/good` и его responder-серт валиден. Ошибка
возникает **до** получения OCSP-ответа (`ocspResponse` пуст, `info` пуст) и **одинакова
для `KC_USE_OCSP` и `KC_USE_CRL`** — значит это фаза валидации цепочки, общая обоим, а
не ревокация. Загрузка CA успешна (`loadCertFile` проверяет rc). Тот же quirk бьёт и
**`VerifyData`-с-cert-time** (`0x08F00042`, `valid=false`), тогда как параллельно
`X509ValidateCertificate(KC_USE_NOTHING)` **успешно** проверяет ту же цепочку
криптографически (`chainSignaturesVerified=true`). Диагностика подтвердила: тот же
контейнер с `CheckCertTime=false` → `valid=true` без ошибки, т.е. подпись математически
верна — падал только cert-time-гейт `VerifyData`. Вывод: это **внутреннее поведение
Kalkan** (либа 2.0.13, версия «unknown» в compat-WARN) для GOST-2015-512-цепочки; нужна
диагностика вендора или более свежая либа.

> **Митигация (реализовано, `core.Verify`): cert-time-anchor override.** Когда
> `VerifyData`-с-cert-time отвергает подпись на `0x08F00042`, а наша **независимая**
> проверка подтверждает валидность — (1) математика подписи через повторный `VerifyData`
> **без** cert-time-гейта, (2) криптопроверка цепочки до доверенного якоря
> (`chainSignaturesVerified` + `trustAnchorFound`, GOST-capable через
> `X509ValidateCertificate(KC_USE_NOTHING)`), (3) каждый серт подписанта в окне действия
> (считаем в Go) — домен ставит `valid=true` и добавляет warning `verify:
> cert-time-anchor-override`. Это **строго сильнее** монолитного бита `VerifyData` (все
> три факта обязаны сойтись), а не слабее; ревокация тут ни при чём (обычный `verify` её
> и не делает). Гейт: только при включённой `trust.verify-chain`.

### Эмпирически подтверждено (v2.0.13, functional-тест)

Прогон против реального Kalkan + тестовый НУЦ (`TestFunctional_Revocation`):

- **Own-fetch CRL + library-verify работает.** Скачиваем CRL своим `http.Client` →
  отдаём **файл** в `X509ValidateCertificate(KC_USE_CRL)`: свежий → `rc=0` (подпись+
  свежесть проверены, good), протухший → **`0x08F0005D` «CRL has expired»**. Передача
  файла и enforcement свежести — на стороне Kalkan.
- **`KC_SetProxy(off)` → `rc=0`**, последующая операция не ломается.
- **OCSP ловит отзыв, которого нет в CRL.** Тестовый revoked-серт: OCSP → `revoked`
  (`certificateHold`), а его **свежий** базовый CRL — `good` (серт не в списке).
- **CRL: свежесть ≠ полнота + base↔delta может быть рассогласован (durable).** Отзыв
  произошёл *в середине* окна валидности базового CRL (между `thisUpdate` и
  `nextUpdate`). CDP и Freshest-CRL в самом серте указывают **ровно на два CRL** —
  базовый и delta; другого источника у серта нет. У тестового НУЦ оба **заморожены на
  одну дату** (переиздания в окне нет), delta **пуст**, и вдобавок **несогласованы**:
  delta построен относительно `BaseCRLNumber=167`, а по URL отдаётся базовый
  `CRLNumber=166` (delta требует базу новее опубликованной). Итог: отзыв через CRL
  недостижим — только OCSP.
- **Требование к нашему CRL-слою:** проверять свежесть (`nextUpdate`) **и**
  согласованность base↔delta (`delta.BaseCRLNumber ≤ base.CRLNumber`, `AKI` совпадает);
  при устаревании/рассогласовании/пустоте — **падать на OCSP**, а не «доверять» неполному
  CRL как отрицательному ответу.

**Рекомендация (уточнённая, подтверждённая эмпирически).** Свой CRL-слой — для сетевого
контроля и офлайн-покрытия, но для надёжного «reject revoked» он **недостаточен в
одиночку**: **OCSP авторитетен для real-time статуса**. Держать OCSP основной онлайн-
проверкой (делегированной Kalkan), CRL — контролируемым нами fallback/офлайн-слоем с
проверкой свежести и base↔delta-согласованности, а не единственным источником.

## OCSP-кэш ответов (стейплинг)

`internal/ocspcache` + порт `core.OCSPCache` (`trust.ocsp-cache`, off по умолчанию).
Кэшируется **ответ**, а не HTTP-обмен: запрос к респондеру делает сама Kalkan,
поэтому попадание в кэш пропускает нативный вызов целиком — это и снижает нагрузку
на `pki.gov.kz`, и даёт стейплинг (сырой OCSP-ответ хранится рядом с вердиктом и
отдаётся при `wantOcsp`).

- **Свежесть — от респондера:** запись живёт до `nextUpdate` ответа, но не дольше
  `trust.ocsp-cache-ttl` (10m) для ответов без `nextUpdate` — там респондер ничего
  не обещал.
- **`revoked` кэшируется дольше** (24h): отзыв монотонен, вердикт назад не
  откатывается, и это заодно не даёт отозванному серту проскочить, пока респондер
  недоступен.
- **Ключ включает URL респондера** — ответ тест-PKI не подставится в прод-проверку.
- **Ошибки не кэшируются** — иначе сбой закрепил бы сам себя на весь TTL.
- Только OCSP-путь; CRL отвечает из материала, который уже есть у CRL-слоя.
- Метрика `qoltanba_ocsp_cache_total{result=hit|miss}`.
