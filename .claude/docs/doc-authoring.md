# Написание reference-док

Читать перед созданием или изменением reference-доки в `.claude/docs/` (включая `.claude/docs/features/`). Эти доки держат контекст, не выводимый из одного лишь кода.

## Загружаются по требованию — никогда по умолчанию

Доки НЕ загружаются в каждую сессию. К каждой ведёт указатель в `CLAUDE.md`; эта загрузка по требованию и есть механизм Progressive Disclosure для док — поэтому держать доки вне контекста по умолчанию и есть весь смысл.

- Новая reference-дока получает одну строку-буллет в списке **Reference-доки** в `CLAUDE.md`.
- Новая фича-дока идёт в `.claude/docs/features/<feature>/` и получает строку в таблице **Фича-доки**, указывающую на её `index.md`, с триггер-словами.
- Указатель *и есть* триггер: назови конкретную область/термины, которые должны заставить читателя открыть доку. Одна строка.

## Фича-доки: директория-на-фичу, три тира

Фича-дока — это **директория**, а не один файл — чтобы задача загружала только нужный ей срез (Progressive Disclosure *внутри* фичи, а не только на её границе). Монолитный файл фичи заставляет каждую задачу платить за всё целиком; разбивай.

```
features/<feature>/
  index.md            # дешёвая точка входа — читается всегда первой
  <sub-area>.md       # глубокие секции — читать, только когда задача попадает в эту под-область
```

**`index.md` (Тир 1 — дешёвый, ~1–2 КБ, низкая волатильность).** Единственный файл, на который указывает `CLAUDE.md`. Должен содержать, в этом порядке:

1. **Scope** — одна строка о том, что покрыто + «вне области → см. X».
2. **Взгляд с высоты** — вся фича одним взглядом: слои/этапы, через которые проходит запрос (небольшая ASCII-схема хорошо работает) и *почему это важно*. Читатель должен ухватить форму фичи, не открывая ни одной секции.
3. **Gotchas** — неочевидные факты, не выводимые из кода (ловушки именования, «выглядит как X, но это Y», молчаливые переключения на async, ограничения «нельзя менять»). Только-добавление; это самый ценный, наименее восстановимый контент. Выноси в `gotchas.md`, только если перерастает index.
4. **Таблица маршрутизации** — под-область → какой файл секции открыть + триггер-слова. Именно это экономит токены: читатель прыгает сразу в нужную секцию (или нужный исходник), не загружая всё и не гоняя `grep` по пакетам.
5. **Карта файлов и символов** — где что лежит (пакеты, типы, структуры, интерфейсы, enum-ы с путями). Держи карту *только* здесь, чтобы она не дублировалась по секциям. Давай **путь + одну строку роли + максимум неочевидные якорные символы** на запись — не исчерпывающий список тип-за-типом; длинный хвост сворачивай в его пакет.
6. **Связанные фичи** — ссылки на соседние доки.

**`<sub-area>.md` (Тир 2 — глубокий, выше волатильность).** Одна связная под-область на файл (поток, этап, подсистема). Изменчивую детализацию потока клади сюда, не в index. Кросс-линкуй соседние секции и обратно на `index.md` по относительному пути.

Маленьким фичам может хватить только `index.md` + одна-две секции — не разбивай ради разбиения. Тест: если две под-области редко встречаются в одной задаче — им место в разных файлах-секциях. **Разбивай по под-области/потоку, а не по архитектурному слою.** Файл-на-слой (`driver.md`, `domain.md`, `transport.md`) переусложняет — задача режет сквозь слои, так что в итоге открываешь их все. Секция — это связная под-область, этап или поток (`native-library`, `signing-verify`, `validation`); микро-файлы формы слоя (по несколько строк, всегда читаются вместе) должны схлопнуться в под-область-доку, которую они поддерживают.

## Доки — это код, держи их в синхроне

Дока — часть изменения, которое трогает её область, а не мысль-после. Когда код переносит файл, переименовывает символ, меняет поток или делает задокументированный факт неверным — **обнови соответствующую доку в том же изменении**. Дока, отъехавшая от кода, хуже, чем никакой доки — считай устаревшую доку багом. В частности: обновляй карту/маршрутизацию в `index.md`, когда меняются пути или под-области, и обновляй указатель в `CLAUDE.md`, когда меняется область или триггер-слова доки (устаревший триггер = доку никогда не читают).

## Держи каждую доку в рамках

- **Только то, что не выводится из кода** — не структуру, не прошлые фиксы, не то, что фиксирует git. В частности, **не перечисляй то, что воспроизводит один `grep`/`ls`**: списки каждого кода ошибки/структуры/DTO/enum-кейса, всех методов типа, всех файлов в пакете, всех обработчиков транспорта. Это самый быстрый в написании контент и первый, что молча отъезжает. Держи вместо этого: gotchas, потоки, реляционные таблицы (маппинги, не лежащие рядом в коде), магические константы/env/TTL и один неочевидный якорный символ.
- **Замени перечисление голым указателем, а не командой.** Укажи на директорию или файл (`internal/pki/`, `core/service.go`) — читатель умеет `grep`/`ls`/открыть, так что не пиши глагол. Переиспользуй *точный* путь, который перечисление уже назвало, чтобы указатель не стал вторым источником отъезда, и сохрани любой неочевидный факт, что нёс список (HTTP-код, магическую константу, флаг `KC_*` или код `KCR_*`, TTL кэша), короткой заметкой рядом.
- **Никаких жёстких чисел в прозе** («~35 OID-ов», «7 транспортов») — магнит отъезда с нулевой навигационной ценностью. Говори «несколько» / «по домену» или просто назови директорию.
- **Никаких номеров строк в ссылках** — `oids.go:120` отъезжает при каждой правке выше него. Назови файл и символ; это локализует.
- Обычный Markdown, `# Заголовок`. Файлам-секциям frontmatter не нужен.
