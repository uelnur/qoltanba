## 1. Цели и принципы

**Что делаем:** тонкий сервис поверх нативной библиотеки Kalkan, который умеет
подписывать и проверять данные (XML, CMS, WSSE, ZIP), валидировать сертификаты
(OCSP/CRL) и **исчерпывающе** возвращать информацию о подписи, подписантах и
ключах — так, чтобы его легко было встроить в чужую систему.

**Принципы:**

- **Не реализуем криптографию сами** — вся крипта в библиотеке Kalkan; мы делаем
  FFI и удобный API вокруг её готовых методов (`SignXML`/`VerifyXML`,
  `SignData`/`VerifyData`, `SignWSSE`, `X509ValidateCertificate`,
  `X509CertificateGetInfo`, `KC_GetTimeFromSig`, `ZipConSign`/`ZipConVerify`).
- **Одно ядро — много адаптеров.** Крипто-логика не знает о транспорте.
- **Малый след:** один бинарь, низкое и предсказуемое потребление RAM, быстрый
  старт, минимум зависимостей.
- **Исчерпывающие ответы:** из данных и ключа извлекаем всё, что доступно (см. §5).
- **Безопасность по умолчанию:** секреты не попадают в логи/метрики/трейсы/ошибки.
- **Пригодность для open source:** чистое юридическое разделение с проприетарной
  библиотекой Kalkan, высокое покрытие тестами, понятная документация.

**Стек (зафиксировано):** Go 1.22+ с cgo для FFI; сборка нативно под каждую
целевую ОС. Обоснование выбора — в справочнике SDK и в [журнале решений](#16-журнал-нюансов-и-решений) (N0).

## 2. Границы и не-цели

- **Поддерживаемые ОС определяются наличием нативной библиотеки у потребителя:**
  Linux x64 и Windows x64/x86 (то, подо что НУЦ поставляет `libkalkancryptwr` /
  `KalkanCrypt.dll`). macOS и мобильные платформы нативной сборки в SDK не имеют —
  **вне области проекта** (для разработки на macOS используется Linux-контейнер).
- **Не встраиваем и не распространяем библиотеку Kalkan** — см. §8.
- Не реализуем UI/фронтенд-подпись (это зона NCALayer).
- Не реализуем собственный УЦ, выпуск сертификатов, TSA/OCSP-серверы — только
  клиентские вызовы к сервисам НУЦ.

## 3. Архитектура

Одно транспортно-независимое ядро, вокруг которого — тонкие адаптеры.

```
  CLI ─┐
 REST ─┤
  UDS ─┤                 core.Service                 internal/native
 gRPC ─┼──►  Sign*/Verify*/CertInfo/Validate  ──►  Provider (FFI, пул воркеров)
Rabbit┤          (Go-структуры, без транспорта)           │
Kafka ┘                    │                              ▼
                           ├── KeySource (§9)   libkalkancryptwr-64.so /
                           └── Observability (§10)         KalkanCrypt.dll
```

Ключевые пакеты:

- **`internal/native`** — единственное место с cgo. Загрузка библиотеки
  (`dlopen`/`LoadLibrary`), `KC_GetFunctionList` → таблица указателей, обёртки
  методов с Go-сигнатурами, паттерн «сначала длина буфера, затем данные»,
  маппинг кодов `KCR_*` в Go-ошибки + человекочитаемый текст
  (`KC_GetLastErrorString`). Реализует интерфейс `Provider`.
- **`Provider` (интерфейс)** — абстракция над крипто-движком. В проде —
  cgo-реализация; в тестах — фейк/мок (см. §12). Это делает почти весь код
  тестируемым без реальной библиотеки.
- **`core`** — операции на Go-структурах, оркестрация: выбор ключа (`KeySource`),
  вызов `Provider`, сбор исчерпывающего ответа, валидация цепочки.
- **`transport/*`** — адаптеры (httprest, socket, grpc, amqp, kafka, cli). Каждый
  включается отдельно (§14), не включён — RAM не тратит.

**Модель параллелизма / потокобезопасность.** Тред-безопасность нативной
библиотеки не гарантирована (косвенный признак — PHP-сборки в вариантах TS/NTS).
Поэтому крипто-вызовы обслуживает **пул из N воркеров**: каждая горутина прибита к
своему OS-потоку (`runtime.LockOSThread`) со своим инициализированным KC-хендлом;
вызовы к одному хендлу сериализованы. N ограничивает и параллелизм, и RAM, и
нагрузку от MQ-консюмеров (они берут слот из пула). Стартовать можно с
mutex-защищённого одиночного контекста и масштабировать по замерам.

## 4. Операции

Базовый набор (v1), каждая доступна из всех транспортов через единый контракт:

| Операция        | Описание                                        | Методы Kalkan                                              |
|-----------------|-------------------------------------------------|------------------------------------------------------------|
| `sign.xml`      | Подпись XML (XMLDSIG/XAdES)                     | `SignXML`                                                  |
| `sign.cms`      | Подпись данных в CMS/PKCS#7 (attached/detached) | `SignData`                                                 |
| `sign.wsse`     | Подпись SOAP/WSSE                               | `SignWSSE`                                                 |
| `sign.zip`      | Подпись ZIP-контейнера                          | `ZipConSign`                                               |
| `sign.hash`     | Подпись предвычисленного хеша                   | `HashData`+`SignHash`                                      |
| `verify.xml`    | Проверка подписи XML                            | `VerifyXML` (+ `KC_getCertFromXML`, `KC_getSigAlgFromXML`) |
| `verify.cms`    | Проверка подписи CMS                            | `VerifyData` (+ `KC_GetCertFromCMS`, `KC_GetTimeFromSig`)  |
| `verify.zip`    | Проверка подписи ZIP                            | `ZipConVerify` (+ `KC_getCertFromZipFile`)                 |
| `cert.info`     | Полный разбор сертификата                       | `X509CertificateGetInfo`                                   |
| `cert.validate` | Валидация по цепочке (OCSP/CRL)                 | `X509ValidateCertificate`                                  |

Флаги форматов (`KC_IN_*`/`KC_OUT_*`, `KC_SIGN_CMS`/`KC_SIGN_DRAFT`,
`KC_DETACHED_DATA`, `KC_WITH_TIMESTAMP` и т.д.) — параметры запроса; полный
перечень в приложениях справочника SDK.

### 4.1. Пакетный режим (batch)

Каждая операция доступна в **пакетном варианте**: на вход — массив элементов
(до конфигурируемого лимита), на выходе — массив результатов **в том же порядке**.

- **Единичный вызов — частный случай пакета** из одного элемента (общий кодовый
  путь, единый контракт; не плодим отдельную логику).
- **Изоляция ошибок:** сбой одного элемента не роняет весь пакет. Для каждого
  элемента — свой статус/`libError`; сводка по пакету (`total`/`succeeded`/
  `failed`). Политика выбирается запросом: `continue-on-error` (по умолчанию) или
  `fail-fast`.
- **Общие параметры пакета:** ключ/`KeySource`, флаги формата, политика валидации
  можно задать один раз на весь пакет и переопределять на уровне элемента.
- **Параллелизм и порядок.** Элементы пакета распределяются по пулу воркеров (§3),
  результаты собираются с сохранением исходного порядка. Конкурентность и объём
  пакета ограничены конфигом — это удерживает RAM и защищает нативную библиотеку.
- **Стриминг для больших пакетов.** Для gRPC — server-streaming результатов; для
  REST — опционально NDJSON-поток, чтобы не держать весь ответ в памяти. MQ
  (Kafka/Rabbit) естественно пакетны: один job = один элемент, либо job-конверт с
  массивом; `correlationId` на элемент.
- **Наблюдаемость:** метрики размера пакета, доли ошибок в пакете, латентности на
  элемент и на пакет (§10).

### 4.2. Асинхронные задания и большие файлы

Синхронный запрос-ответ непригоден для больших файлов (таймауты, всплеск RAM,
раздувание base64 в JSON). Для них — **асинхронная модель заданий (jobs)** и
потоковая обработка.

- **Модель задания.** Клиент отправляет задание → получает `jobId` и `202
  Accepted` → узнаёт результат одним из способов: **опрос** статуса, **webhook-
  callback** по завершении, либо доставка результата через MQ. Жизненный цикл:
  `queued → running → succeeded|failed|cancelled`, с прогрессом, TTL и
  возможностью отмены.
- **Вход/выход по ссылке, а не inline.** Большие данные передаются как **путь к
  файлу** или ссылка на объектное хранилище (S3-совместимое)/стрим-загрузку — не
  как base64 в теле. Это держит RAM низкой и убирает 33% overhead base64.
- **Потоковая обработка и опора на возможности библиотеки.** Где библиотека умеет
  читать файл сама (`KC_IN_FILE`, файловые `ZipConSign`/`ZipConVerify`) — отдаём
  ей путь, не буферизуя данные у себя. Для очень больших входов, где это уместно,
  — схема **hash-streaming → `SignHash`** и **detached-подпись** (не тащим данные
  в подпись).
- **Хранилище состояния заданий.** По умолчанию — в памяти (быстро, эфемерно);
  для устойчивости и горизонтального масштабирования — внешнее (БД/Redis) и/или
  доставка через MQ с семантикой at-least-once + идемпотентность по `jobId`.
- **Backpressure и лимиты.** Большие задания идут через отдельную очередь поверх
  пула воркеров; ограничения по числу параллельных больших заданий, максимальному
  размеру входа и месту под спул на диске — конфигом. Защищает и RAM, и нативную
  библиотеку.
- **Транспорты.** REST: `POST /jobs` → `GET /jobs/{id}` (статус) → `GET
  /jobs/{id}/result`; опциональный `callbackUrl`. gRPC: паттерн long-running
  operation или server-streaming прогресса. MQ (Kafka/Rabbit): изначально
  асинхронны — задание in, результат out по `correlationId`/`jobId`.
- **Наблюдаемость (§10):** метрики глубины очереди заданий, длительности,
  объёма обработанных байт, прогресса; статус по `jobId`.
- **Безопасность (§11):** временные/спул-файлы — с ограниченными правами,
  гарантированной очисткой (в т.ч. при сбое/отмене) и без утечки путей/секретов в
  телеметрию.

Batch (§4.1) и async-large (§4.2) — разные оси и **комбинируются**: пакет может
исполняться как асинхронное задание; большой элемент внутри пакета — обрабатываться
потоково.

## 5. Принцип исчерпывающего извлечения

**Правило:** любой ответ операции разбора/проверки должен содержать **всё, что
библиотека способна извлечь** из входа — не минимально необходимое, а максимум.
Извлечение — **best-effort и по-полевое**: отсутствие/ошибка одного поля не
прерывает разбор; в ответе фиксируется, что удалось, а что нет (с кодом причины).

### Из сертификата / ключа

Через `X509CertificateGetInfo` со всеми `KC_CERTPROP_*`:

- **Издатель (issuer):** country, state/region (SOPN), locality, organization,
  orgUnit, commonName, полный DN.
- **Субъект (subject):** country, SOPN, locality, commonName, givenName, surname,
  **serialNumber (ИИН/БИН)**, email, organization, orgUnit, businessCategory (BC),
  DC, полный DN.
- **Срок:** notBefore, notAfter.
- **Ключ/использование:** keyUsage, extKeyUsage, publicKey, алгоритм подписи,
  authorityKeyId, subjectKeyId, серийный номер сертификата, policy OIDs.
- **Точки распространения (при наличии в версии либы):** OCSP-URL, CRL-URL,
  delta-CRL-URL.

**Производные поля (вычисляем сами из извлечённого):** тип владельца (физ./юр.
лицо), роль (первый руководитель, сотрудник с правом подписи и т.д. — по policy
OID / OU), разобранные ИИН/БИН, семейство алгоритма (RSA / ГОСТ-2004 /
ГОСТ-2015) и длина ключа, признаки назначения (аутентификация/подпись).

### Из подписанных данных (CMS / XML / ZIP)

- **Все подписи**, а не первая: итерируемся по `inCertID`/`inSignID`.
- Для каждого подписанта: встроенный сертификат подписанта (и его полный разбор
  по списку выше), время подписи, **метка времени TSP** (`KC_GetTimeFromSig`),
  алгоритм дайджеста и подписи, attached/detached.
- **Результат проверки** каждой подписи + сырой `outVerifyInfo`.
- **Встроенные артефакты валидности:** OCSP-ответы (флаг `KC_GET_OCSP_RESPONSE` /
  выход `getOCSPResponse`), признаки уровня CAdES (BES/T — по кодам
  `KCR_CADESBES_*`/`KCR_CADEST_*`).
- **XML-специфика:** алгоритм подписи (`KC_getSigAlgFromXML`), подписанные
  узлы/ID, канонизация.
- **ZIP-специфика:** манифест, пофайловые подписи.
- **Цепочка/валидация:** результат `X509ValidateCertificate` — статус по OCSP/CRL,
  построение цепочки до корня.

Что именно доступно — зависит от версии библиотеки и содержимого данных; поэтому
извлечение управляется картой возможностей (§8) и всегда помечает недоступное.

## 6. Контракт данных

Единый JSON-контракт для REST/socket/CLI/MQ; его же зеркало в `.proto` для gRPC.
Бинарные поля — base64. Для асинхронных транспортов обязателен `correlationId`.

Пример ответа проверки (сокращённо, но по духу — «всё, что есть»):

```jsonc
{
  "operation": "verify.cms",
  "valid": true,
  "signatureCount": 2,
  "signers": [{
    "index": 0,
    "subject": { "commonName": "...", "surname": "...", "givenName": "...",
                 "serialNumber": "IIN000000000000", "iin": "000000000000",
                 "organization": null, "bin": null, "email": "...",
                 "country": "KZ", "locality": "...", "dn": "..." },
    "issuer":  { "commonName": "ҰЛТТЫҚ КУӘЛАНДЫРУШЫ ОРТАЛЫҚ...", "dn": "..." },
    "ownerType": "individual",          // производное
    "roles": ["signature"],             // производное из policy OID/OU
    "certSerial": "...", "notBefore": "...", "notAfter": "...",
    "keyAlgorithm": "gost2015-512", "signatureAlg": "gost34310-gost34311",
    "keyUsage": ["digitalSignature","nonRepudiation"],
    "authorityKeyId": "...", "subjectKeyId": "...", "policyOids": ["1.2.398..."],
    "signingTime": "2026-07-04T10:00:00+05:00",
    "timestamp": { "present": true, "time": "2026-07-04T10:00:01+05:00",
                   "tsaSerial": "..." },
    "cadesLevel": "CAdES-T",
    "validation": { "type": "OCSP", "status": "GOOD", "checkedAt": "...",
                    "ocspResponseB64": "..." },
    "certPem": "-----BEGIN CERTIFICATE-----..."
  }],
  "verifyInfo": "<сырой outVerifyInfo>",
  "extraction": {                        // что удалось/не удалось (best-effort)
    "warnings": [ { "field": "signers[0].issuer.email",
                    "reason": "KCR_GETCERTPROPERR" } ]
  },
  "libError": null                       // либо { "code":"0x08F0001c", "text":"..." }

```

Каждое поле «best-effort»: недоступные — `null` + запись в `extraction.warnings`,
а не отказ всей операции.

### Проверено пробником (`tools/probe/FINDINGS.md`)

Форматы и правила ниже подтверждены прогоном против реальной либы v2.0.13 и
тестовых ключей всех профилей:

- `X509CertificateGetInfo` возвращает **UTF-8 строки вида `имя=значение`**
  (`C=KZ`, `serialNumber=IIN123456789011`, `notBefore=08.05.2026 06:45:13 +00:00`),
  NUL-терминированные → в контракте префикс `имя=` **срезаем**, дату нормализуем
  из `DD.MM.YYYY HH:MM:SS ±HH:MM` в RFC3339.
- **Отсутствие поля** → код `0x08F00038` (`KCR_GETCERTPROPERR`) — это норма
  (у профиля нет такого поля), в ответе `null`, а не ошибка.
- **Производные поля подтверждены данными:**
  - `iin` ← `SUBJECT_SERIALNUMBER` (`IIN<12>`); `bin` ← `SUBJECT_ORGUNIT_NAME`
    (`OU=BIN<12>`).
  - `ownerType`: нет `OU(BIN)` → физлицо; есть `OU(BIN)`+ФИО/ИИН → сотрудник ЮЛ;
    есть `OU(BIN)`, нет ФИО/ИИН → информационная система.
  - `roles` ← OID в `EXT_KEY_USAGE`: `…3.3.4.1.1` физлицо; `…3.3.4.1.2` ЮЛ;
    `.2.1` первый руководитель, `.2.2` право подписи, `.2.5` сотрудник,
    `.2.6` инфосистема; казначейство — `1.2.398.5.19.1.2.2.1`.
    (`certificatePolicies` у тестовых одинаков — роль по нему не различить.)
- **verify**: успех определяется **кодом возврата = 0**, а `outVerifyInfo` даже на
  успехе содержит OpenSSL-строку `error:00000000:...` (нули = «нет ошибки»).
- **sign/verify** используют **одинаковый набор флагов**; проверка срока
  сертификата идёт по системным часам → нужен явный параметр,
  отключающий её (`KC_NOCHECKCERTTIME`), иначе `0x08F00042` (`KCR_CERTTIMEINVALID`).

**Полнота извлечения подтверждена (все операции прогнаны):**

- **Цепочка** `chain[]` (leaf → НУЦ → КУЦ): в подписи вложен **только лист**
  (как и у NCANode — см. `docs/COMPARISON-ncanode.md` §3a); промежуточный/корневой
  достраиваются из **CA-источника** + `X509ValidateCertificate`. Три источника CA:
  (1) доверенный bundle потребителя; (2) дозагрузка по AIA листа (проверено);
  (3) конфигурируемые URL со скачиванием и кэшем + рефреш (паттерн NCANode) —
  дефолтный набор берём из **официального реестра КУЦ РК**
  (`https://root.gov.kz/registr/`, снимок в `internal/pki/ca-registry.json`:
  корни КУЦ, НУЦ, аккредитованные УЦ + корневые CRL).
  Полная цепочка требует CA-источника → в ответе — признак «неполная/нет якоря
  доверия». В ответе мы отдаём **полную цепочку** (NCANode — только лист).
  CA-уровни отличаются по `keyUsage=keyCertSign cRLSign` и отсутствию EKU.
- **Валидация**: OCSP (онлайн, проверено на живом сервисе) даёт `good` (rc 0) или
  `revoked` + `reason`/`revocationTime` (rc 1) + base64 OCSP-ответа; CRL —
  офлайн по файлу.
- **Подписант** извлекается из CMS (`KC_GetCertFromCMS`) и XML
  (`KC_getCertFromXML`), индексы **1-based**; `VerifyXML` даёт per-signature инфо.
- **Множественная подпись** (co-sign разными людьми) поддержана и проверена: все
  подписанты извлекаются перебором `sigId`, каждый — с полным разбором (проверено
  на физлице + первом руководителе ЮЛ). `signers[]` — массив с явными полями;
  **индекс ≠ порядок подписания** (в CMS обратный XML) — не опираться на порядок.
  Верификация мультиподписи требует загруженных доверенных CA-сертов.
- **Оригинальное содержимое**: у **attached**-подписи вложено и **восстанавливается**
  (`VerifyData`, `inData=NULL`, без `KC_OUT_PEM`); у **detached** — не хранится в
  подписи (нужен отдельный вход); у XML enveloped — сам документ и есть содержимое.
  Признак detached — часть ответа контракта.

## 7. Транспорты и интеграция

Все — тонкие адаптеры над `core`, включаются флагами (§14).

| Транспорт | Библиотека | Модель |
|-----------|-----------|--------|
| CLI | `cobra`/stdlib `flag` | процесс: вход в stdin, JSON в stdout |
| HTTP REST | stdlib `net/http` + `chi` | тот же `http.Server` слушает TCP **или Unix-socket** |
| Unix-socket / named pipe | как REST/gRPC | локальный IPC без сетевого порта |
| gRPC | `google.golang.org/grpc` | типизированный контракт `.proto` |
| RabbitMQ | `rabbitmq/amqp091-go` | consume job → publish в reply-queue по `correlationId`; ack после публикации результата |
| Kafka | `twmb/franz-go` | consumer group → result-topic; commit offset после успеха |

Асинхронные (Rabbit/Kafka): идемпотентность через `correlationId`, ограничение
конкурентности пулом воркеров, ретраи/DLQ по политике потребителя.

## 8. Bring-Your-Own-Library и проверка совместимости

### 8.1. Почему не храним библиотеку

Библиотека Kalkan — проприетарная, права на распространение у НУЦ РК / АО «НИТ».
**Мы её не кладём в репозиторий, не публикуем и не встраиваем в артефакты.**
Каждый потребитель самостоятельно получает библиотеку у НУЦ и указывает путь к
ней. Репозиторий защищается от случайного коммита бинарников (см. §13).

### 8.2. Конфигурирование библиотеки и её зависимостей

Потребитель задаёт:

- путь к основной библиотеке (`libkalkancryptwr-64.so` / `KalkanCrypt.dll`);
- **зависимости движка** (проверено пробником, см. `tools/probe/FINDINGS.md`):
  `libkalkancryptwr` требует **`libkalkancrypto.so`** — это OpenSSL-**1.1**-форк
  Kalkan (даёт символы `SRP_*` и др., удалённые в OpenSSL 3.x → на системном
  OpenSSL 3 без форка загрузка падает); плюс `libltdl7`, `zlib1g`,
  `libpcsclite1`, `libm`, и совместимость с **iconv** (либа собрана против GNU
  libiconv). Это часть проверки совместимости среды;
- каталог **ca-certs** (корневые/промежуточные для OCSP/CRL) и драйверы токенов
  (PKCS#11) для аппаратных хранилищ;
- ожидаемую **версию** библиотеки (см. 8.3) и политику совместимости.

### 8.3. Загрузка и проверка совместимости

Так как библиотеку контролирует потребитель, при старте выполняется
многоступенчатая проверка (fail-fast по умолчанию):

1. **Наличие и загрузка.** Файл существует, разрядность совпадает, `dlopen`/
   `LoadLibrary` успешен, экспортируется символ `KC_GetFunctionList`.
2. **Заполнение таблицы функций и карта возможностей.** Проверяем, что нужные
   указатели ненулевые. Структура `stKCFunctionsType` **росла между версиями**
   (напр. `UVerifyData`, zip-методы, `KC_InitDebug` добавлены позже) — это **ABI-
   риск**: старая библиотека вернёт более короткую таблицу, чтение «хвостовых»
   методов небезопасно. Поэтому фиксируем **минимальную поддерживаемую версию** и
   строим **карту возможностей** (`capabilities`) — какие операции реально
   доступны; недоступные операции корректно отключаются в API.
3. **Определение версии.** У C-API нет функции версии. Источники (по приоритету):
   явно заданная в конфиге версия → имя файла (`...so.2.0.13`) → эвристика по
   возможностям. Версия сверяется с **матрицей совместимости** проекта
   (протестированные версии). Неизвестная версия → по политике: `strict`
   (отказ) / `warn` (работать, но пометить в статусе и метриках).
4. **Смоук-самотест (обязательный, без ключа).** `KC_Init`, затем детерминированный
   прогон: `HashData` над фиксированным вектором и сверка с эталонным дайджестом
   (для каждого поддерживаемого алгоритма). Это доказывает, что библиотека не
   только загрузилась, но и **считает корректно**.
5. **Глубокий самотест (опциональный, с тестовым ключом потребителя).** Полный
   round-trip `sign → verify` на **предоставленном потребителем** тестовом ключе
   (свой мы не поставляем — см. §8.1). Включается флагом; при провале — по политике.

Результаты проверки (версия, карта возможностей, статус самотестов) публикуются в
`/readyz` и метриках (§10). **Готовность сервиса (readiness) = успешная загрузка +
обязательный самотест.** До этого сервис не принимает трафик.

### 8.4. Диагностика

Ошибки загрузки/совместимости — с чётким кодом и подсказкой (несовпадение
разрядности, отсутствующий символ, старая версия, провал самотеста, отсутствие
зависимостей движка/ca-certs). Никаких секретов в диагностике.

## 9. Источники ключей

Не навязываем один способ — потребители разные. Абстракция **`KeySource`** с
несколькими реализациями, выбираемыми потребителем; плюс **встроенный простой
keystore** для тех, кто не хочет строить своё.

| Режим | Как задаётся ключ | Кому подходит | Замечания по безопасности |
|-------|-------------------|---------------|---------------------------|
| **Inline** | PKCS#12 (base64) + пароль **в запросе** | Быстрый старт, stateless-интеграции | Секрет в запросе → только по TLS/локальному сокету; не логировать; держать в памяти эфемерно |
| **Путь на сервере** | путь к `.p12` + пароль из секрета/env | Сервер владеет ключами | Пароль вне запроса |
| **По `keyId`** | ссылка на запись в настроенном keystore | Централизованное управление ключами | В запросе только `keyId`, без секретов |
| **Аппаратный токен** | тип хранилища (`KCST_KAZTOKEN`/`KZIDCARD`/…) + PIN | Токены/ID-карты | PIN — секрет; те же правила |
| **Встроенный keystore** | наш простой зашифрованный стор + admin-API/CLI (`add/list/remove`) | Тем, кому нужно «из коробки» | Мастер-ключ/пароль стора вне репо; см. §11 |

Единый интерфейс для `core`, поэтому добавление источника (например, HashiCorp
Vault, KMS) — это новая реализация `KeySource` без изменения операций.
Встроенный keystore — **опциональный** компонент, по умолчанию выключен.

Во всех режимах пароли/PIN/материал ключа — **секреты** (§11): не попадают в логи,
метрики, трейсы, тела ошибок и эхо-ответы.

## 10. Наблюдаемость

Потребитель должен «видеть» статус и живость сервиса из коробки — **без утечки
секретов**.

- **Проверки состояния:**
  - `/healthz` (liveness) — процесс жив.
  - `/readyz` (readiness) — библиотека загружена и прошла обязательный самотест
    (§8.3); иначе трафик не принимается.
  - `/statusz` (info) — версия сервиса и сборки, обнаруженная версия библиотеки,
    карта возможностей, uptime, включённые транспорты, размер/загрузка пула
    воркеров. **Без путей к секретам и без чувствительных значений.**
- **Метрики (Prometheus `/metrics`):** число и латентность запросов по операциям
  и транспортам; ошибки по кодам `KCR_*`; занятость/сатурация пула воркеров;
  in-flight и глубина очередей MQ; статус самотеста библиотеки; счётчики
  «unknown lib version». Кардинальность лейблов ограничена (никаких DN/ИИН в
  лейблах).
- **Логи (structured, `log/slog`):** уровни, `correlationId`/`traceId`,
  операция, коды результата. **Полезная нагрузка и любые секреты не логируются**
  (тела данных — только по явному debug-флагу и без секретов). Разделяем
  операционный лог и (опционально) аудит-лог событий подписи (в аудите — субъект,
  серийник, операция, результат, время; **не** ключ/PIN/данные).
- **Трейсинг (опционально, OpenTelemetry):** спаны на операцию, проброс
  `traceparent`/`correlationId` через все транспорты, включая MQ.

Вся observability включается/выключается конфигом; порт метрик/health может быть
отделён от рабочего порта.

## 11. Безопасность и гигиена секретов

Сквозной принцип, обязательный для всех подсистем (§9, §10).

- **Что считается секретом:** приватный ключ и его байты (PKCS#12), пароли к
  контейнерам, PIN токенов, мастер-пароль встроенного keystore, содержимое
  подписываемых данных (потенциально ПДн).
- **Где секреты запрещены:** логи, метрики (значения и лейблы), трейсы, тела
  ошибок, ответы-эхо, `/statusz`, дампы конфигурации, отладочный вывод.
- **Меры:** централизованная редакция при сериализации; типы-обёртки
  (`Secret[T]`) с безопасным `String()`/маршалингом; запрет логировать
  request/response целиком; эфемерное хранение ключевого материала в памяти и
  затирание после использования (насколько позволяет рантайм); секреты — только
  из env/файлов-секретов/секрет-менеджеров, не из аргументов CLI и не из репозитория.
- **Транспорт:** inline-режимы ключей — только по TLS или локальному сокету;
  рекомендации по mTLS/авторизации для сетевых транспортов.
- **Линт/тесты:** проверки, что структуры логов/ошибок не содержат секретных полей
  (см. §12).

## 12. Стратегия тестирования

Цель — высокое покрытие при том, что **реальной библиотеки Kalkan в репозитории и
CI нет** (её нельзя распространять, §8.1).

- **Абстракция `Provider` (§3) делает почти весь код тестируемым без библиотеки.**
  Ядро, транспорты, `KeySource`, сбор исчерпывающего ответа, редакция секретов —
  тестируются с **фейковым Provider**.
- **Уровни тестов:**
  - *Unit* — логика ядра, парсинг/сборка контракта, производные поля (тип
    владельца, ИИН/БИН, семейство алгоритма), редакция секретов.
  - *Contract* — соответствие REST/gRPC/CLI/MQ единому контракту (golden-файлы).
  - *Loader/ABI* — тесты загрузчика и самотеста против **поддельной нативной
    библиотеки** (крошечная `.so`/`.dll`, экспортирующая `KC_GetFunctionList` со
    стаб-таблицей), чтобы прогнать `dlopen`, карту возможностей, определение
    версии, обязательный самотест — **без настоящей крипты**.
  - *Integration* — с **настоящей** библиотекой; включаются build-тегом/переменной
    окружения (путь к либе + тестовый ключ потребителя), запускаются локально или
    на self-hosted-раннере, где библиотека есть. В обычном CI не обязательны.
  - *E2E* — поднятие сервиса и прогон через каждый транспорт (интеграционный
    контур, с реальной либой).
  - *Fuzz* — устойчивость парсеров входа (XML/CMS/ZIP, base64, границы буферов).
- **Гейты качества:** целевое покрытие для `core`/транспортов (напр. ≥ 80–90%),
  проверка «нет секретов в телеметрии», проверка «нет проприетарных бинарников в
  репо» (§13). Точные пороги — в [открытых вопросах](#15-открытые-вопросы).

## 14. Конфигурация

Единый источник конфигурации (флаги + env + файл), секреты — только через
env/секрет-файлы. Ориентировочный набор (уточняется):

```
# библиотека
--lib-path /opt/kalkan/libkalkancryptwr-64.so
--lib-version 2.0.13            # для матрицы совместимости
--lib-compat strict|warn
--ca-certs-dir /opt/kalkan/ca-certs
--selftest-deep --selftest-key <path>   # опциональный глубокий самотест
# воркеры
--workers 4
# транспорты (включаются по мере задания)
--http :8080  --socket /run/kalkan.sock  --grpc :9090
--amqp-url ...  --kafka-brokers ...
# ключи
--keystore-mode inline|path|keyid|token|builtin
--builtin-keystore-dir ...     # если включён встроенный стор
# наблюдаемость
--metrics :9095  --log-level info  --otel-endpoint ...  --log-payloads=false
```

## 17. Глоссарий

- **Kalkan** — криптобиблиотека НУЦ РК (ЭЦП, ГОСТ/RSA); ядро всей крипты.
- **BYOL** — Bring-Your-Own-Library: библиотеку предоставляет потребитель.
- **CMS/PKCS#7** — формат подписанных/зашифрованных сообщений.
- **XMLDSIG/XAdES** — стандарты подписи XML.
- **WSSE** — WS-Security, подпись SOAP.
- **OCSP/CRL** — онлайн-проверка статуса / список отзыва сертификатов.
- **TSP/TSA** — протокол/служба меток времени.
- **ИИН/БИН** — индивидуальный/бизнес-идентификационный номер (в `serialNumber` субъекта).
- **Provider** — внутренняя абстракция над крипто-движком (для тестируемости).
- **KeySource** — внутренняя абстракция над источником ключа.
- **Карта возможностей (capabilities)** — какие операции реально поддержаны загруженной версией библиотеки.
