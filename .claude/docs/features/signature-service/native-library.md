# Нативная библиотека: BYOL, совместимость, самотест

Часть фичи `signature-service` — сначала прочитай [`index.md`](index.md).
Здесь — **сервисные** аспекты работы с библиотекой (политика, проверки при старте,
параллелизм). Сама механика C-API (загрузка, зависимости среды, функции, флаги,
коды) — в самодостаточном справочнике [`../../kalkan-api/`](../../kalkan-api/index.md).

## Bring-Your-Own-Library

Библиотека Kalkan — проприетарная (права у НУЦ РК / АО «НИТ»). **Не хранится в
репозитории, не публикуется, не встраивается в артефакты.** Путь к ней и её
зависимостям (OpenSSL-1.1-форк, iconv, pcsclite и т.д. — перечень в
[`../../kalkan-api/loading.md`](../../kalkan-api/loading.md)) задаёт потребитель;
репозиторий защищается от коммита `*.so`/`*.dll`/`*.p12`. Отсюда — обязательная
проверка совместимости при старте (зависит от версии либы у потребителя).

**Граница BYOL — рантайм-бинарник и ключевой материал, не заголовок API.**
Исключается загружаемая библиотека (`*.so`/`*.dll`/`*.dylib`) и секреты
(`*.p12`/ключи) — то, что даёт потребитель. Заголовок C-API
`internal/native/KalkanCrypt.h` **намеренно закоммичен**: cgo-shim (`shim.c`)
компилируется против структуры таблицы функций `stKCFunctionsType`, а сами вызовы
резолвятся в рантайме через `dlsym`/`KC_GetFunctionList` (`.so` не нужен для
сборки). Это API-декларация, а не сама библиотека — поэтому shim собирается и
юнит-тесты/CI идут **без** нативной либы (`dlopen` — только в рантайме). Копия в
`native/include/` (из SDK потребителя) остаётся под `.gitignore`; истина для
сборки — закоммиченная копия в драйвере.

## Карта возможностей и версия

Таблица функций Kalkan растёт между версиями (ABI-риск — см.
[`../../kalkan-api/loading.md`](../../kalkan-api/loading.md)). Драйвер строит
**карту возможностей** (какие операции реально доступны у загруженной либы, через
`kc_has` по таблице функций) и корректно отключает недоступные в API. Функции
версии в C-API нет → определяется по конфигу (`lib.version`) → **резолву симлинка** → имени файла
(`...so.2.0.13`) → эвристике.

> **Почему резолв симлинка.** Разворачивают обычно неверсионированный
> `libkalkancryptwr-64.so`, который ссылается на `...so.2.0.13` — в имени самой ссылки
> версии нет, и без резолва каждый запуск писал `libVersion: "unknown"`,
> `compat: "degraded"` на совершенно исправной библиотеке.

**Минимальная поддерживаемая версия** — `lib.min-version` (дефолт `2.0.0`;
переопределяемо). Ниже минимума → несовместимо; неизвестная/непарсимая версия →
предупреждение (не блок). Это открытый вопрос по стартовой матрице версий
([`architecture.md`](../../architecture.md)), поэтому порог — конфигурируемый, а не
захардкоженный факт.

**Политика при несовместимости** — `lib.compat=strict|warn|off` (дефолт `strict`):
`strict` не даёт стартовать при любой несовместимости; `warn` стартует, но громко
логирует; `off` только отдаёт отчёт. **Провал смоук-самотеста всегда блокирует**,
независимо от политики (либа, считающая неверно, непригодна).

## Самотест и готовность

- **Смоук (обязательный, без ключа):** `HashData(SHA256)` над фиксированным
  вектором → сверка с `crypto/sha256` того же входа в Go. Кросс-проверка своим
  же дайджестом означает, что **эталонная константа не хранится** (её и не нужно
  подбирать под версию); допускаются кодировки вывода raw/hex/base64. Доказывает,
  что либа не только загрузилась, но и **считает верно**. Провал (посчитала и
  ошиблась) — жёсткий отказ; `HashData` отсутствует → самотест пропущен
  (предупреждение «корректность не доказана», не отказ).
- **Глубокий (опциональный, с тестовым ключом потребителя):** round-trip
  sign→verify (свой ключ не поставляем).
- **Readiness = загрузка + обязательный самотест;** до этого сервис не принимает
  трафик.

**Оценка совместимости** (`internal/compat`, cgo-free) собирает факты драйвера
(версия, карта возможностей, самотест) в детальный отчёт с per-check вердиктами
(load / version / self-test / required-capabilities / optional-capabilities) и
итоговым `compatible|degraded|incompatible`. Требуемые возможности зависят от
режима: всегда `VerifyCMS`+`CertInfo`(+`Validate`), плюс `SignCMS` вне
`verify-only`; остальное — опционально (нехватка → `degraded`, не блок).

**Где видно:** подкоманда `lib-check` (`… lib-check -lib-path … [-json]`) печатает
отчёт и выходит ненулевым при несовместимости (диагностика, вне политики); при
старте сервиса отчёт логируется и гейтит запуск по `lib.compat`; сводка (`selfTest`,
`compat`-вердикт) уходит в `/statusz`.

## Потокобезопасность

Тред-безопасность нативной либы не гарантирована → крипто-вызовы обслуживает **пул
воркеров** (`internal/native.Pool`, реализует порт `provider.Provider`): каждый
воркер прибит к своему OS-потоку (`runtime.LockOSThread`) со своим экземпляром
библиотеки; запросы идут в общую очередь, вызовы к одному экземпляру
сериализованы. N (`PoolSize`) ограничивает параллелизм, RAM и нагрузку от
MQ-консюмеров. Порт объявлен в `internal/provider` (cgo-free), драйвер маппит в
него `KCR_*`-коды и C-типы — наружу они не протекают.

### Изоляция экземпляров (проверено на v2.0.13, эмпирически)

«Каждый воркер — свой Kalkan» требует **отдельной копии состояния криптодвижка**,
иначе конкурентная работа рушит процесс. Что выяснено прогонами против реальной
либы:

- **Общий `dlopen` враппера + пул>1 — НЕБЕЗОПАСНО.** Мутабельное состояние
  (ключи, движок) живёт в **`libkalkancrypto.so`** (OpenSSL-1.1-форк, грузится
  один раз через `LD_PRELOAD`). Конкурентный `KC_LoadKeyStore` из разных воркеров
  → `double free`/`SIGABRT`.
- **Копии враппера с разным soname — НЕ помогают:** изолируют глобалы враппера,
  но `libkalkancrypto` остаётся общей → тот же креш.
- **`dlmopen(LM_ID_NEWLM)` — работает, но с нюансом.** Новый линк-неймспейс тянет
  СВОЮ копию всех объектов (включая `libkalkancrypto`) → изоляция состояния. НО:
  в новом неймспейсе `LD_PRELOAD` не действует, а `dlmopen` **не принимает
  `RTLD_GLOBAL`** («invalid mode»), поэтому внешние символы враппера (`SRP_*`,
  `libiconv_*`, `floor`, `g_rgSCardT0Pci`) туда так не внести. Решение: вшить
  зависимости в **`DT_NEEDED` самого враппера** (`patchelf --add-needed` по
  абсолютным путям к iconv-шиму/`libkalkancrypto`/`libm`/`libpcsclite`), тогда
  неймспейс самодостаточен. Один патченный файл → `dlmopen(LM_ID_NEWLM)` из него
  N раз даёт N независимых экземпляров. **Проверено:** пул из 4 выдержал 40
  конкурентных sign+verify.
- **Дефолт — `PoolSize=1`** (общий `dlopen`, сериализация): безопасно и без
  patchelf/Linux-специфики. `Isolated=true`+`PoolSize>1` включает изоляцию; если
  неймспейс не собрался — `Open` **отказывает** (не поднимает небезопасный пул).
- Механизм изоляции инкапсулирован в `internal/native` (шов `openInstance` /
  `prepareNamespaceWrapper`) — домен и транспорт про него не знают. Альтернатива
  для сред без patchelf — пул **процессов** (изоляция адресным пространством);
  порт `Provider` это допускает без правок домена.
- **Загрузчик кросс-платформенный (`shim.c`).** POSIX-ветка — `dlopen`/`dlsym`;
  Windows-ветка (`#ifdef _WIN32`) — `LoadLibraryEx(..., LOAD_WITH_ALTERED_SEARCH_PATH)`
  (чтобы `KalkanCrypt.dll` подтянул соседние `libcrypto/libssl.dll` из своей папки)
  + `GetProcAddress`. `-ldl` линкуется только не под Windows (`#cgo !windows`).
  **Изоляция (`dlmopen`+`patchelf`) — только Linux:** под Windows пул работает в
  shared-режиме (`PoolSize=1`), как и любая non-linux сборка. Кросс-сборка —
  `GOOS=windows CGO_ENABLED=1 CC=<mingw>-gcc` (см. `release.yml` / windows-джобу CI).

Функциональная проверка модели — `test/functional/` (linux/amd64-контейнер,
`LD_PRELOAD`, тег `qoltanba_functional`), тест `TestFunctional_PoolIsolation`.

## Ошибки

Коды `KCR_*` маппятся в типизированные Go-ошибки + человекочитаемый текст
(`KC_GetLastErrorString`). Значения и толкование — в
[`../../kalkan-api/reference.md`](../../kalkan-api/reference.md). Диагностика
загрузки — с чётким кодом (разрядность, отсутствующий символ, старая версия, провал
самотеста), **без секретов**.
