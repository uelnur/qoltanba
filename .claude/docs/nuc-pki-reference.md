# Справочник PKI НУЦ/КУЦ РК (OID, роли, алгоритмы)

Авторитетные таблицы инфраструктуры открытых ключей РК: арка OID `1.2.398`,
роли в EKU, политики TSA, соответствия алгоритмов, разбор DN и вывод ИИН/БИН/пола.
Эти факты **не выводятся из кода** — они заданы стандартами НУЦ/КУЦ и подтверждены
эмпирически. Всё, что материализуется в коде (`internal/pki/*.json`, генераторы),
берёт значения отсюда, а не хардкодит их «по памяти».

**Источники истины (онлайн):**

- **OID** — официальный реестр КУЦ РК: <https://root.gov.kz/oid/> (вся арка
  `1.2.398`: роли/EKU, политики, TSA, зарегистрированные ИС). Снимок целиком —
  `internal/pki/oids-nuc.json` (генератор `tools/oidgen/fetch_oids.py`).
- **CA / trust-store** — реестр КУЦ РК: <https://root.gov.kz/registr/> (корни КУЦ
  gost/rsa/2015/2020, НУЦ, УЦ ГО, аккредитованные УЦ + корневые CRL). Снимок —
  `internal/pki/ca-registry.json` (генератор `tools/oidgen/fetch_ca_registry.py`,
  доступ из Go — `internal/pki/ca.go`).

> Роли и имена OID берём из реестра, а не из чужих хардкод-таблиц. Таблицы ниже —
> рабочий минимум для навигации; полнота — в снимках JSON.

**Продакшн-эндпоинты РК** (в доках/примерах чаще фигурирует тестовый контур
`test.pki.gov.kz`; боевые — здесь): OCSP `http://ocsp.pki.gov.kz/`, TSP
`http://tsp.pki.gov.kz/`, CRL НУЦ `crl.pki.gov.kz/nca_{rsa,gost}_2022.crl` (+ delta
`nca_d_*`), CRL КУЦ `crl.root.gov.kz/{gost,rsa,gost2020,rsa2020}.crl`, CA-серты
`pki.gov.kz/cert/…` и `root.gov.kz/cert/…`. Не завязываться на один хост — AIA
промежуточного может указывать на `root.gov.kz`.

## Роли владельца — OID в `extendedKeyUsage`

Роль сертификата кодируется **OID-ами в EKU** (расширение `2.5.29.37`), а не в
`certificatePolicies` (у тестовых профилей политика одна — `1.2.398.3.3.2` — и роль
по ней не различить). Префикс роли — `1.2.398.3.3.4`.

| OID | Роль |
|-----|------|
| `1.2.398.3.3.4.1.1` | Физлицо (INDIVIDUAL) |
| `1.2.398.3.3.4.1.2` | Юрлицо — базовый маркер (ORGANIZATION) |
| `1.2.398.3.3.4.1.2.1` | Первый руководитель (CEO) |
| `1.2.398.3.3.4.1.2.2` | Право подписи (CAN_SIGN) |
| `1.2.398.3.3.4.1.2.3` | Право подписи фин. документов (CAN_SIGN_FINANCIAL) |
| `1.2.398.3.3.4.1.2.4` | Кадровик (HR) |
| `1.2.398.3.3.4.1.2.5` | Сотрудник (EMPLOYEE) |
| `1.2.398.3.3.4.1.2.6` | Информационная система |
| `1.2.398.3.3.4.2` … `.2.3` | Привилегии УЦ: NCA_PRIVILEGES / ADMIN / MANAGER / OPERATOR |
| `1.2.398.3.3.4.3` … `.3.2.1` | Идентификация: очная / удалённая / remote-digital-id |

Стандартные EKU (`serverAuth`/`clientAuth`/`E-mail Protection`) в набор ролей не
входят — при маппинге отбрасываются. Полный перечень (15+ OID) — в
`internal/pki/oids-nuc.json`; маппинг подтверждён эмпирически на тестовых ключах
всех профилей (физлицо, первый руководитель, сотрудник, право подписи, инфосистема,
казначейство).

## Соответствия алгоритмов

Ключ выбора — **OID алгоритма подписи сертификата** (`signatureAlgorithm`).

OID подписи ГОСТ-2015: `1.2.398.3.10.1.1.2.3.1` (256), `1.2.398.3.10.1.1.2.3.2`
(512). Старый ГОСТ 34.310/34.311 — ветка по умолчанию.

**signOID → digest CMS:**

| signOID | digest |
|---------|--------|
| `1.2.840.113549.1.1.5` (sha1WithRSA) | SHA1 `1.3.14.3.2.26` |
| `1.2.840.113549.1.1.11` (sha256WithRSA) | SHA256 `2.16.840.1.101.3.4.2.1` |
| `1.2.398.3.10.1.1.2.3.1` (GOST2015-256) | GOST3411-2015-256 |
| `1.2.398.3.10.1.1.2.3.2` (GOST2015-512) | GOST3411-2015-512 |
| иначе (старый ГОСТ) | GOST34311-95 `1.2.398.3.10.1.1.1.1` |

**signOID → XML-URI** (`[signatureMethod, digestMethod]`): RSA — `xmldsig-more#`;
ГОСТ-2015 — `urn:ietf:params:xml:ns:pkigovkz:xmlsec:algorithms:gostr3410…/gostr3411…`;
старый ГОСТ — `xmldsig-more#gost34310-gost34311` / `#gost34311`.

**Нюанс TSP — ОПРОВЕРГНУТО ЗАМЕРОМ (2026-08-23).** Прежде здесь стояло «hash
TSP-запроса для любого ГОСТ = старый `GOST34311`». Прогон против **боевого TSA**
`test.pki.gov.kz/tsp/` с ГОСТ-2015-ключом показал обратное: `messageImprint` токена
несёт OID **`1.2.398.3.10.1.3.3` = ГОСТ Р 34.11-2015 (512)**, 64 байта, при политике
`1.2.398.3.3.2.6.4` (`TSA_GOST2015_POLICY`). То есть TSA хеширует запрос тем же
поколением, что и подпись, а не старым 34.311-95.

**Следствие:** `messageImprint` для ГОСТ-2015 **нечем пересчитать через Kalkan** —
`HashData` в v2.0.13 знает только `KC_HASH_SHA256` и `KC_HASH_GOST95`; любое
написание 2015 (`GOST3411_2015_512/256`, оба OID ветки `1.2.398.3.10.1.3.*`) даёт
`0x08F00015 «Hash Data - unknown algorithm»`. В заголовке `KalkanCrypt.h` флага для
2015-хеша нет вовсе. Подпись самого токена при этом проверяется штатно: TimeStampToken —
это CMS SignedData, и `VerifyData` его верифицирует (замерено на том же прогоне).
Что из этого следует для `cadesLevel` — в
[`features/signature-service/signing-verify.md`](features/signature-service/signing-verify.md).

**Арка хеширования — `1.2.398.3.10.1.3.*`** (по официальному реестру `oids-nuc.json`):
`.3.1` = ГОСТ 34.11-95, `.3.2` = ГОСТ Р 34.11-2015 (256), `.3.3` = ГОСТ Р 34.11-2015 (512).
Не путать с `1.2.398.3.10.1.1.1*`, которую использует таблица ниже.

**hash-OID → имя** (заполняет `tspHashAlgorithm` и digest-поля):

| OID | Имя | | OID | Имя |
|-----|-----|-|-----|-----|
| `1.3.14.3.2.26` | SHA1 | | `2.16.840.1.101.3.4.2.1` | SHA256 |
| `2.16.840.1.101.3.4.2.2` | SHA384 | | `2.16.840.1.101.3.4.2.3` | SHA512 |
| `2.16.840.1.101.3.4.2.4` | SHA224 | | `1.2.840.113549.2.5` | MD5 |

## Разбор DN → поля субъекта

Значения RDN мапятся по ключу (регистронезависимо). Числовые OID для DER-разбора:

| RDN | OID | Поле |
|-----|-----|------|
| `CN` | `2.5.4.3` | commonName |
| `SURNAME` / `SN` | `2.5.4.4` | фамилия (lastName) |
| `SERIALNUMBER` | `2.5.4.5` | ИИН **или** БИН (см. ниже) |
| `C` | `2.5.4.6` | country |
| `L` | `2.5.4.7` | locality |
| `S` / `ST` | `2.5.4.8` | state (SOPN) |
| `O` | `2.5.4.10` | organization |
| `OU` | `2.5.4.11` | orgUnit (несёт БИН) |
| `GIVENNAME` / `G` | `2.5.4.42` | имя/отчество (givenName) |
| `E` / `EMAILADDRESS` | `1.2.840.113549.1.9.1` | email |
| `businessCategory` | `2.5.4.15` | BC (напр. Казначейство) |
| `DC` | `0.9.2342.19200300.100.1.25` | domainComponent |

**ИИН/БИН:**

- **ИИН** ← `SERIALNUMBER` с префиксом `IIN` → срезать `^IIN` (12 цифр).
- **БИН** ← `OU` с префиксом `BIN` → срезать `^BIN` (12 цифр); либо `SERIALNUMBER`
  с префиксом `BIN`.
- **serialNumber самого сертификата** (не путать с RDN) = HEX. Формат-ловушка при
  сверке: у некоторых реализаций это `BigInteger.toString(16)` — **без ведущих
  нулей, нижний регистр, знаковый**. Kalkan `X509CertificateGetInfo` отдаёт HEX в
  **верхнем** регистре (`CERT_SN`). При кросс-сверке приводить к одному виду.

**Пол (gender)** — не хранится в сертификате, выводится из 7-й цифры ИИН
(ГГММДД **S** …): 1/3/5 → мужской, 2/4/6 → женский, иначе NONE.

Кириллица в значениях — UTF-8 (теги DER: UTF8String `0x0C`, PrintableString `0x13`,
BMPString `0x1E` = UTF-16BE).
