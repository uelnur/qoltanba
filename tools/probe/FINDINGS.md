# Пробник Kalkan — эмпирические находки для проектирования контрактов

Результаты прогона `tools/probe` против **реальной** библиотеки Kalkan
(`libkalkancryptwr-64.so` v2.0.13) и тестовых ключей НУЦ РК (GOST-2015, пароль
`Qwerty12`). Цель — выяснить, какие данные реально извлекаются, в каком формате,
и что нужно на входе. Это фактическая база для §5/§6 (контракты) и §8 (среда)
в `docs/DESIGN.md`.

Прогон выполнялся в контейнере `linux/amd64` (нативная либа — только Linux/x64).

---

## 1. Находки по среде выполнения (важно для §8 BYOL)

Чтобы `libkalkancryptwr-64.so` вообще загрузилась, потребовалось разрешить
символы, которых нет в её `NEEDED`:

| Символ / зависимость | Откуда берётся | Вывод |
|----------------------|----------------|-------|
| `SRP_Calc_A` и др. OpenSSL | **`libkalkancrypto.so`** (OpenSSL-1.1-форк Kalkan из `KalkanCrypt-OpenSSL`) | Либе нужен **OpenSSL 1.1**; в системном OpenSSL 3.x эти символы удалены → загрузка падает. Нужно грузить `libkalkancrypto.so` (LD_PRELOAD/LD_LIBRARY_PATH). |
| `g_rgSCardT0Pci` | `libpcsclite.so.1` | Нужен PC/SC (`libpcsclite1`). |
| `floor` | `libm.so.6` | Нужна libm. |
| `libiconv`, `libiconv_open`, `libiconv_close` | **GNU libiconv** | Либа собрана против GNU libiconv; в glibc функции зовутся `iconv*`. Мы подкладываем шим-алиас (`iconv_compat.c`). |
| `libltdl.so.7`, `libz.so.1`, `libpcsclite.so.1` | пакеты `libltdl7 zlib1g libpcsclite1` | из `NEEDED`. |

**Вывод для проекта:** требования к среде потребителя (§8) должны включать
`libkalkancrypto.so` (OpenSSL-1.1-форк из комплекта), `libltdl7`, `zlib1g`,
`libpcsclite1`, `libm`, и совместимость с `iconv`. На хостах с OpenSSL 3 без
форка Kalkan библиотека не загрузится — это часть проверки совместимости.

Рабочая цепочка (зашита в `Dockerfile` пробника):
```
LD_PRELOAD="/opt/iconv_compat.so /usr/lib/x86_64-linux-gnu/libm.so.6 \
            /usr/lib/x86_64-linux-gnu/libpcsclite.so.1 /native/lib/libkalkancrypto.so"
```

## 2. Формат вывода `X509CertificateGetInfo`

- Все значения — **UTF-8 строки**, NUL-терминированные, в фиксированных/дополненных
  буферах (нужно резать по первому `\x00`). Кириллица — как есть (UTF-8).
- **Значение приходит с префиксом имени поля**: `C=KZ`, `CN=…`, `GN=…`, `SN=…`,
  `serialNumber=IIN…`, `notBefore=…`, `keyUsage=…`. → В контракте префикс до `=`
  нужно **срезать** (и/или отдавать и raw, и parsed).
- **Отсутствующее поле** → код `0x08F00038` (`KCR_GETCERTPROPERR`). Это **не
  ошибка**, а «поля нет в сертификате» → в контракте `null`, а не провал операции.
- Форматы конкретных полей (пример физлица):

| Свойство | Пример значения | Формат / примечание |
|----------|-----------------|---------------------|
| `SUBJECT_DN` | `CN = ТЕСТОВ ТЕСТ, SN = ТЕСТОВ, serialNumber = IIN123456789011, C = KZ, GN = ТЕСТОВИЧ` | агрегат RDN, разделитель `, `, пробелы вокруг `=` |
| `SUBJECT_SERIALNUMBER` | `serialNumber=IIN123456789011` | ИИН как `IIN<12 цифр>` |
| `SUBJECT_ORGUNIT_NAME` | `OU=BIN123456789021` | у ЮЛ содержит **БИН** как `BIN<12>` |
| `SUBJECT_ORG_NAME` | `O=АО "ТЕСТ"` | название организации (у ЮЛ) |
| `SUBJECT_BC` | `businessCategory=KS1234` | только у некоторых профилей (Казначейство) |
| `NOTBEFORE` / `NOTAFTER` | `notBefore=08.05.2026 06:45:13 +00:00` | **`DD.MM.YYYY HH:MM:SS ±HH:MM`** (со смещением tz) |
| `CERT_SN` | `certificateSerialNumber=6C4256…` | HEX (верхний регистр) |
| `AUTH_KEY_ID` / `SUBJ_KEY_ID` | `authorityKeyIdentifier=FAD24B…` / `subjectKeyIdentifier=EC4256…` | HEX |
| `KEY_USAGE` | `keyUsage=digitalSignature nonRepudiation keyAgreement` | список через пробел |
| `EXT_KEY_USAGE` | `extendedKeyUsage=E-mail Protection (1.3.6.1.5.5.7.3.4); 1.2.398.3.3.4.1.2 (…); …` | человекочит. + OID, разделитель `; ` |
| `SIGNATURE_ALG` | `signatureAlgorithm=GOST R 34.10-2015 with GOST R 34.11-2015 (512 bit)(1.2.398.3.10.1.1.2.3.…)` | текст + OID |
| `PUBKEY` | `MIGsMCMGCSqDDgMK…` | **base64** DER (SubjectPublicKeyInfo) |
| `POLICIES_ID` | `certificatePolicies=1.2.398.3.3.2` | OID(ы) политик |

## 3. Различия по типам ключей (профилям)

Прогон по 6 профилям набора `2026.05.08-2027.05.07`. `+` = поле присутствует
(rc=0), `.` = отсутствует (`KCR_GETCERTPROPERR`).

```
PROP                     Физлицо  Перв.рук  Сотруд  ПравоПодп  ИнфоСист  Казнач
SUBJECT_GIVENNAME           +        +        +        +          .        +
SUBJECT_SURNAME             +        +        +        +          .        +
SUBJECT_SERIALNUMBER(ИИН)   +        +        +        +          .        +
SUBJECT_ORG_NAME            .        +        +        +          +        +
SUBJECT_ORGUNIT_NAME(БИН)   .        +        +        +          +        +
SUBJECT_BC                  .        .        .        .          .        +
SUBJECT_DC                  .        .        .        .          .        +
(остальные — присутствуют у всех: DN, серийники, KU/EKU, даты, алг., pubkey, policies)
```

Наблюдения для контракта:

- **Физлицо**: есть ФИО+ИИН, нет ORG/OU.
- **ЮЛ-персона** (первый рук. / сотрудник / право подписи): ФИО+ИИН **и** ORG+OU(БИН).
- **Информационная система**: **нет** ФИО/ИИН (это не человек), есть ORG+OU(БИН).
- **Казначейство клиент**: как ЮЛ-персона + `businessCategory` и `DC`.
- Отсюда `ownerType` выводится по наличию полей:
  - есть OU(BIN)+ФИО/ИИН → **сотрудник ЮЛ**;
  - есть OU(BIN), нет ФИО/ИИН → **информационная система**;
  - нет OU(BIN) → **физлицо**.

### Роль кодируется OID в EKU (`extendedKeyUsage`)

| Профиль | Роль-OID в EKU |
|---------|----------------|
| Физлицо | `1.2.398.3.3.4.1.1` |
| ЮЛ (базовый маркер) | `1.2.398.3.3.4.1.2` |
| Первый руководитель | `1.2.398.3.3.4.1.2.1` |
| Сотрудник с правом подписи | `1.2.398.3.3.4.1.2.2` |
| Сотрудник организации | `1.2.398.3.3.4.1.2.5` |
| Информационная система | `1.2.398.3.3.4.1.2.6` |
| Казначейство клиент | `1.2.398.5.19.1.2.2.1` |

→ В контракте роль (`roles`) выводится маппингом этих OID; `certificatePolicies`
у всех тестовых один (`1.2.398.3.3.2`) и роль по нему не различить.

## 4. Поведение sign / verify (для контрактов операций)

- **Подпись CMS** (`SignData`, флаги `KC_SIGN_CMS|KC_OUT_PEM`): успешна для всех
  профилей. Вывод — PEM-блок `-----BEGIN CMS-----…-----END CMS-----`.
- **Важно:** без флага `KC_NOCHECKCERTTIME` подпись вернула
  `0x08F00042` (`KCR_CERTTIMEINVALID`) — библиотека сверяет срок сертификата с
  системными часами. → В контракте нужен явный параметр «не проверять срок»
  и корректная обработка этого кода.
- **Проверка** (`VerifyData`): вызывается **с теми же флагами, что и подпись**, и
  ей передаются исходные данные + подпись (подтверждено эталоном SDK `test.cpp`).
  При неверных флагах → `0x08F00039` (`KCR_SIGNFORMMAT`).
- `outVerifyInfo` даже при успехе содержит OpenSSL-строку вида
  `error:00000000:lib(0):func(0):reason(0)` (нули = «нет ошибки»). → **Успех
  определяется кодом возврата (0), а не текстом `verifyInfo`.**
- **Метка времени** (`KC_GetTimeFromSig`) на подписи без TSP → `0x08F0004A`
  (`KCR_NOTSATOKEN`). Для проверки извлечения метки нужен флаг `KC_WITH_TIMESTAMP`
  при подписи и доступ к TSA (`test.pki.gov.kz`) — сетевой вызов.

## 4a. Цепочка сертификатов

**Единого вызова, возвращающего `[leaf, intermediate, root]`, в API нет.** Цепочка
строится так:

1. Загрузить CA-сертификаты в либу: `X509LoadCertificateFromFile(path, KC_CERT_CA)`
   для корня (КУЦ) и `KC_CERT_INTERMEDIATE` для промежуточного (НУЦ).
2. Каждый уровень разбирается тем же `X509CertificateGetInfo` (все поля).
3. Порядок восстанавливается по `authorityKeyIdentifier` (AKI) листа =
   `subjectKeyIdentifier` (SKI) издателя; корень самоподписан
   (`SUBJECT_DN == ISSUER_DN`).
4. `X509ValidateCertificate` при валидации сам печатает цепочку в `outInfo`
   («Verify chain and certificates: CN=…НУЦ…\nCN=…leaf…»).

Построенная цепочка (тестовый набор):
```
leaf (владелец):     CN=ТЕСТОВ ТЕСТ
intermediate (НУЦ):  CN=ҰЛТТЫҚ КУӘЛАНДЫРУШЫ ОРТАЛЫҚ (GOST) TEST 2022
root (КУЦ):          CN=НЕГІЗГІ КУӘЛАНДЫРУШЫ ОРТАЛЫҚ (GOST) TEST 2022
```

**CA-уровни отличаются от листа по полям:** у промежуточного и корневого
`keyUsage=keyCertSign cRLSign` и **нет `extendedKeyUsage`** (rc `0x08F00038`); у
листа — `digitalSignature nonRepudiation keyAgreement` + EKU с роль-OID. Это
надёжный признак «это CA» при разборе цепочки.

**Важно: цепочка НЕ вложена в подпись.** По ASN.1 в CMS лежит **только сертификат
подписанта (лист)** — промежуточного (НУЦ) и корневого (КУЦ) в подписи нет
(проверено: `KC_GetCertFromCMS` отдаёт лист; второго серта в `CMS.certificates`
нет). Цепочка **достраивается** из внешнего источника:

1. **из доверенного CA-набора** потребителя (BYOL) — как делает пробник:
   подгружает `root`/`nca` и `X509ValidateCertificate` строит цепочку;
2. **скачиванием по AIA** — лист несёт расширения (проверено):
   - AIA CA Issuers → `http://test.pki.gov.kz/cert/nca_gost2022_test.cer` (серт НУЦ),
   - AIA OCSP → `http://test.pki.gov.kz/ocsp/`,
   - CRL DP → `http://test.pki.gov.kz/crl/nca_gost2022_test.crl`,
   - CPS → `http://pki.gov.kz/cps`.

Что вложено — зависит от подписанта: дефолтный `SignData` НУЦ кладёт только лист;
CAdES-профили с полной цепочкой вложили бы все серты в `CMS.certificates` (тогда
`KC_GetCertFromCMS` вернул бы и промежуточные). → В контракте `chain[]` —
best-effort: гарантирован лист из подписи, полная цепочка **требует CA-источника**;
признак «цепочка неполная / нет якоря доверия» отдаём в ответе.

**Достройка по AIA реализована в пробнике (`aiaWalk`) и проверена онлайн.** Без
локальных CA-файлов: из DER листа берётся URL `CA Issuers` (регэксп по `…\.cer`),
издатель скачивается по HTTP, разбирается через Kalkan, и обход идёт вверх, пока
есть ссылка (у корня её нет). Результат — та же цепочка leaf → НУЦ → КУЦ:
```
leaf → http://test.pki.gov.kz/cert/nca_gost2022_test.cer  → CN=…НУЦ… (16 полей)
НУЦ  → http://root.gov.kz/cert/root_test_gost_2022.cer     → CN=…КУЦ… (16 полей, корень)
```
Замечание: AIA промежуточного указывает на **другой хост** (`root.gov.kz`), а не
`test.pki.gov.kz` — при дозагрузке нельзя завязываться на один домен. Для
безопасности в проде: таймауты, лимит числа переходов, кэш скачанных CA, и
доверять итоговому корню только если он есть в trust-store потребителя.

## 4b. Валидация (CRL / OCSP)

`X509ValidateCertificate(cert, validType, validPath, checkTime, outInfo, …, flag,
getOCSPResponse, …)`:

- **OCSP** (`validType=KC_USE_OCSP`, `validPath="http://…/ocsp/"`, сетевой вызов) —
  проверено на живом тестовом сервисе:
  - **валидный** серт → rc `0x00000000`, `outInfo`:
    `OCSP: check certificate status: good … certificateSerialNumber=… This Update: … Next Update: …`,
    и при флаге `KC_GET_OCSP_RESPONSE` — **base64 OCSP-ответа** (~6.4 КБ);
  - **отозванный** серт → rc `0x00000001`, `outInfo`:
    `OCSP: check certificate status: revoked … Reason: certificateHold … Revocation Time: …`.
  → Статус (good/revoked/unknown) — из rc **и** из текста `outInfo`.
- **CRL** (`validType=KC_USE_CRL`, `validPath=путь к .crl`) — печатает построенную
  цепочку и данные сертификата в `outInfo`; в офлайн-прогоне вернула rc
  `0x08F0005D` (нестандартный код — вероятно, устаревший/неполный офлайн-CRL).
  Для надёжной онлайн-проверки статуса предпочтителен OCSP.

## 4c. Извлечение сертификата подписанта из CMS и XML

- **CMS:** `KC_GetCertFromCMS(cms, len, sigId, flags, out, &len)` — `sigId`
  **1-based**, `flags=KC_IN_PEM|KC_OUT_PEM`. Возвращает PEM сертификата подписанта
  → разбирается тем же `X509CertificateGetInfo` (получены все 19 значимых полей).
- **XML round-trip** (все rc `0x00000000`):
  - `SignXML(alias, flags, xml, …, nodeId, parentNode, parentNs)` — узлы можно
    пустые; вывод — подписанный XML (enveloped).
  - `VerifyXML` → `outVerifyInfo` в структурированном виде:
    `Signature N 1\nId = 1\ncertificateSerialNumber=…\nsignatureAlgorithm=…` —
    **по каждой подписи** (N 1, N 2…), с серийником и алгоритмом подписанта.
  - `KC_getSigAlgFromXML` → `signatureAlgorithm=GOST R 34.10-2015 with GOST R 34.11-2015 (512 bit)(1.2.398.3.10.1.1.2.3.2)`.
  - `KC_getCertFromXML(xml, len, sigId, …)` (`sigId` 1-based) → PEM сертификата
    подписанта → полный разбор.

## 4d. Восстановление оригинального содержимого

Да — **всё извлекается**: и полная информация о подписанте, и **оригинальное
содержимое** (для вложенных подписей).

- **Attached-CMS** (по умолчанию у `SignData` без `KC_DETACHED_DATA`): содержимое
  **вложено** в подпись. Подтверждено ASN.1: внутри `pkcs7-signedData` есть
  `pkcs7-data` → `OCTET STRING` с исходными байтами. Восстанавливается через
  `VerifyData` с `inData=NULL` и флагами `KC_SIGN_CMS|KC_IN_PEM` **без**
  `KC_OUT_PEM` (иначе либа оборачивает контент в PEM и отдаёт пусто):
  ```
  recoveredContent = "Hello, Қазақстан 2026 — тест ЭЦП / qoltanba probe"  // rc=0
  ```
- **Detached-CMS** (`KC_DETACHED_DATA`): содержимого в подписи нет **по определению**
  — оригинал нужно подавать отдельно (в `inData`), восстановить из подписи нельзя.
- **XML (enveloped)**: подписанный документ **сам является** содержимым — данные
  лежат в подписанных узлах XML, доступны напрямую.

**Вывод:** сервис отдаёт по подписи максимум — подписант (полный разбор
сертификата), алгоритм, время/метка времени, per-signature инфо, статус
валидации (OCSP/CRL), **и оригинальное содержимое, если подпись вложенная**.
Признак «detached» (нет вложенного контента) — часть ответа контракта.

## 4e. Множественная подпись (co-signing разными людьми)

Проверено: один документ подписывают **двое разных людей**, и извлекается полная
информация о **каждом** подписанте.

- **Как подписать вторым:** `SignData` принимает предыдущую подпись в параметре
  `inSign` → добавляет ещё один `signerInfo` в тот же CMS. Для XML — повторный
  `SignXML` над уже подписанным документом (добавляется второй `<Signature>`).
  Ключи переключаются повторным `KC_LoadKeyStore` (alias для PKCS12 пустой).
- **Извлечение всех подписантов:** перебор `sigId` **1-based** через
  `KC_GetCertFromCMS` / `KC_getCertFromXML` — каждый серт разбирается полностью.
  Тест: подписант A = физлицо, B = первый руководитель ЮЛ → извлечены оба, с
  раздельными ИИН/ORG/ролью/серийником:
  ```
  CMS: signRC=0 verifyRC=0  (2 подписанта)
    #1 первый руководитель (ORG=АО "ТЕСТ", serial …B1355AABBE4E)
    #2 физлицо             (serial …857727CF8451)
  XML: signRC=0            (2 подписанта)
    #1 физлицо  #2 первый руководитель
  ```
- **Нюанс порядка (важно для контракта):** индекс `sigId` ≠ порядок подписания и
  различается по форматам — в CMS первым идёт **последний** добавленный
  (`#1=B, #2=A`), в XML — **первый** (`#1=A, #2=B`). → Нельзя привязывать смысл к
  индексу; порядок/роли определять по данным (время подписи, идентичность серта).
- **Нюанс верификации:** проверка **мультиподписанного XML** вернула
  `0x08F00022` (`KCR_LOADTRUSTEDCERTSERR`) — для верификации нужны загруженные
  доверенные CA-серты (в проде — загрузить перед verify). **Извлечение
  подписантов от этого не зависит** и работает. Проверка мультиподписи CMS —
  `rc=0` (обе подписи валидны).

## 5. Выводы для контрактов (§5/§6 DESIGN.md)

1. Каждое поле извлекается независимо; **отсутствие поля — норма** (`KCR_GETCERTPROPERR`
   → `null`), не ошибка всей операции. Это подтверждает принцип best-effort.
2. Значения приходят как `имя=значение` → в ответе отдавать **очищенное** значение
   (+ опционально raw и `id/rc` для диагностики).
3. Производные поля контракта, подтверждённые данными: `ownerType`
   (individual / legal-entity-person / infosystem), `iin` (из `serialNumber=IIN…`),
   `bin` (из `OU=BIN…`), `roles` (из EKU-OID), `keyAlgorithm` (из `signatureAlgorithm`/OID).
4. Даты — единый формат `DD.MM.YYYY HH:MM:SS ±HH:MM`; в контракте нормализовать в RFC3339.
5. Флаги — часть входного контракта операций; verify обязан использовать тот же
   набор, что и sign. Нужен явный параметр про проверку срока (`KC_NOCHECKCERTTIME`).
6. **Цепочка** — отдельная сущность контракта: `chain[]` (leaf→intermediate→root),
   каждый уровень с полным разбором; CA-уровни помечаются по `keyUsage=keyCertSign
   cRLSign` + отсутствию EKU. Требует, чтобы потребитель предоставил CA-серты.
7. **Валидация** возвращает `status` (good/revoked/unknown), `reason` и
   `revocationTime` (для revoked), `thisUpdate/nextUpdate`, и сырой OCSP-ответ
   (base64). Источник — OCSP (онлайн) или CRL (офлайн); в контракте — параметр
   выбора и оба результата.
8. **Подписант** извлекается и из CMS (`KC_GetCertFromCMS`), и из XML
   (`KC_getCertFromXML`); индексы подписей **1-based**; `VerifyXML` даёт
   структурированный per-signature `outVerifyInfo`.
9. **Множественная подпись** (co-sign разными людьми) поддержана: все подписанты
   извлекаются перебором `sigId`, каждый — с полным разбором. Индекс ≠ порядок
   подписания (и различается CMS/XML) → в контракте `signers[]` с явными полями,
   без опоры на порядок; верификация мультиподписи требует загруженных CA-сертов.

## 6. Как воспроизвести

```
# NATIVE_DIR должен содержать:
#   lib/libkalkancryptwr-64.so  lib/libkalkancrypto.so
#   keys/<profile>.p12
#   ca/root.pem ca/nca.pem ca/root_test_gost_2022.cer ca/nca_gost2022_test.cer ca/*.crl
NATIVE_DIR=/path/to/native KEY_FILE=fiz.p12 ./run.sh
# множественная подпись (два человека): указать второй ключ
NATIVE_DIR=/path/to/native KEY_FILE=fiz.p12 KEY2_FILE=ur_ruk.p12 ./run.sh
```
Пробник печатает JSON-отчёт в stdout и человеко-читаемый лог в stderr. Примеры
отчётов — `sample-report.json` (валидный) и `sample-report-revoked.json`
(отозванный, статус OCSP `revoked`). Покрытые операции: разбор сертификата (все
профили), цепочка + разбор каждого уровня, **достройка цепочки по AIA из сети**,
валидация CRL/OCSP, sign/verify CMS, восстановление содержимого, извлечение
подписанта из CMS, sign/verify XML + алгоритм + извлечение подписанта,
**множественная подпись CMS/XML двумя людьми + извлечение всех подписантов**.
Примеры: `sample-report.json`, `sample-report-revoked.json`,
`sample-report-multisign.json`.
